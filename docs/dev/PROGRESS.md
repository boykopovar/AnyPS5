# Progress reporting

[`tools/progress.py`](../../tools/progress.py) generates `progress.json`, HTML, SVG maps and badges. The [Pages workflow](../../.github/workflows/pages.yml) publishes them with the web converter after pushes to `main` that change the converter, the web page or these tools. The [Pages progress workflow](../../.github/workflows/pages-progress.yml) runs after pushes that change `core/libs/prx`, the observed manifests or the opcode list, compares the generated `progress.json` with the deployed one and dispatches the Pages workflow only when they differ, so the history chart gains new days only when the progress changes. The [Progress report workflow](../../.github/workflows/progress-report.yml) compares the base and head trees of pull requests.

## Library counts

The scanner reads `APS5_VABI` function definitions under `core/libs/prx/<library>/`, excluding `tests` subdirectories and their descendants. Test callbacks do not contribute to library counts. Definitions whose names end in `_nid_no_patch` or `_nid_no_patch_cut` are internal helpers and are not counted, unless an `APS5_EXPORT` in the library exports them under an explicit name. A definition is pending, a stub, when its body calls `NotImplemented_nid_no_patch`, directly or through a recognized local stub wrapper; [Observed imports](#observed-imports) explains which stubs the headline percentage counts. Call matching uses complete identifiers and accepts whitespace or comments before `(`. Other definitions are counted as implemented. Braces inside string literals, character literals and comments do not delimit bodies. These counts describe declared functions, not every firmware export, verified ABI compatibility or playable games. Silent behavior and unverified assumptions remain in [Technical debt](TechnicalDebt.md).

A library with no scanned definitions can include a sibling library's source builder. The scanner recognizes literal `include(${CMAKE_CURRENT_SOURCE_DIR}/../<library>/<file>.cmake)` references, including quoted paths. It does not evaluate arbitrary CMake expressions. It also recognizes a top-level `.cpp` that includes another library's source with `#include "prx/<library>/<file>.cpp"`.

For these wrappers, the JSON group adds `shared_sources` with the source library's directory name. Its own counts and name lists remain empty. The HTML table links to the source library instead of showing `0/0`; the source library's map tooltip lists its wrappers. Global totals count the definitions at the source library once.

A library with no scanned definitions and no shared sources, such as one whose `Export.cpp` only has `APS5_DUMMY_FUN` because its functions are implemented in another library, is listed as having no exports instead of `0/0`. It is left out of the map.

## Observed imports

A function is in one of three states. An implemented function does not call `NotImplemented_nid_no_patch`. A NID is observed when any measured use shows it is needed, anywhere: the imports of any title or module, any dump or audit run, and what is needed before a title's own code runs, such as what the loader or system startup requires. A pending function is an observed stub when its NID is listed in the library's manifest, and an unobserved stub when it is not. The word is "unobserved", not "unused": the evidence is only that no measured use has shown the function to be needed, which does not prove that nothing ever calls it.

The library percentage is implemented functions over implemented functions plus observed stubs, so unobserved stubs do not lower it. Every implemented function counts, observed or not, so implementing a function never lowers a number. The figure that counts every declared function is kept next to it and nothing is hidden: `progress.json` has `declared_total` and `declared_percent` beside `total` and `percent`, and the progress page has an Implemented, Observed stubs and Unobserved stubs column for each library plus a Declared % column. The map draws implemented functions in green, observed stubs in red and unobserved stubs in grey; the grey is the same colour as the not-implemented GPU shader instructions, and the legend has one grey entry for both, "Unobserved stub (libraries) / Not implemented (shaders)". The page says how many of the pending functions are unobserved.

A manifest is `docs/dev/observed/<library>.txt`, named after a directory of `core/libs/prx`. It holds one 11-character NID per line, sorted and without repeats. `#` starts a comment, and a whole-line comment can head the file. Each NID line carries a provenance tag as its comment, one of `audit: <tool> <date>` (a dump or title import report: `import_audit` or `audit_dump` and the UTC date of the run, never a title name), `loader` (needed before a title's own code runs, such as what the loader or system startup requires, optionally followed by a reason) or `manual: <reason>` (a written reason is required). A line without a tag is untagged: it still counts as observed, `observed_imports.py check` lists it, and the scan records it as `untagged`. An unknown tag is an error. The files hold only NIDs, never title names, so they do not identify the dumps they came from. A NID is matched to a function the way `tools/import_audit.py` matches it: from the name, or from the `APS5_EXPORT` alias, ignoring the `_nid_postfix` and `_nid_disambigN` suffixes.

The default is unobserved: a library with no manifest file has an empty set of observed NIDs, so every pending stub in it is an unobserved stub, and a stub becomes observed only when a manifest names its NID. A manifest is only as complete as the measurements behind it, so a library only changes state when someone adds its file. Each group lists, in `done_unobserved_names`, the implemented functions no manifest names; comparisons report them as "implemented but not observed anywhere".

[`tools/observed_imports.py`](../../tools/observed_imports.py) maintains the files. Audit a title or a module, then merge the JSON of the audit; use `entry` for a NID that another measurement shows is needed:

```sh
python3 tools/import_audit.py REGISTRY... --libs BUILT_PRX_DIR --json audit.json
python3 tools/audit_dump.py DUMP --relinker RELINKER --libs BUILT_PRX_DIR --json audit.json
python3 tools/observed_imports.py add audit.json
python3 tools/observed_imports.py add --check audit.json
python3 tools/observed_imports.py entry libSceExample AbCdEfGhIjK --tag manual --reason "resolved by name with sceKernelDlsym"
python3 tools/observed_imports.py check
```

`add` writes the NIDs of every implemented, partial and stub import to the manifest of each library that provides it, sorted and merged with what is there; it rejects a library that is not in `core/libs/prx` and a malformed NID, and writes nothing when it fails. `add --check` writes nothing and fails when a manifest would change. `entry` adds one NID and requires its provenance tag. `check` validates the committed files, rejects unknown tags and lists the entries that have no tag, as does the `observed-manifest` rule of [`tools/check_conventions.py`](../../tools/check_conventions.py) for the files a pull request changes.

The manifests in the repository were first filled from public texts (pull requests, issues, comments, reviews, discussions, commit messages and docs): a NID is listed, tagged `manual: reported in PR #N`, `issue #N`, `comment #N` or `found in commit <sha>`, when the text shows a title, homebrew or an application using or needing that exact function. A statement that no title reaches a function, a link to another emulator's source and a request for call sites were not accepted. They hold no dumps and no console measurements, so they undercount; only the libraries that have a listed NID have a manifest, and every other library has none, so all its stubs are unobserved. Because the default is unobserved, the headline (implemented functions over implemented functions plus observed stubs) is very high while little evidence exists, and the declared figure next to it is the one that shows how much is declared.

The import audit reads what the relinker resolves at load time, so it misses functions a title looks up at run time with `sceKernelDlsym` by name. A manifest can therefore undercount, and an unobserved stub can still be called by some title; the same holds for needs that no audit or other measurement has reached yet. Add such a NID by hand with the evidence, and do not implement or declare exports without evidence from a measured use that they are needed: [`tools/stubgen.py`](../../tools/stubgen.py) output for NIDs with no such evidence is inventory only.

## Where a stub comes from

Three records say where each stub and each observation comes from. All of them are optional, none changes a count, and none holds a title name.

- Origin of a declaration. `python3 tools/progress.py --origins DIR` (or `--json --origins`) adds an `origins` object to every library group, keyed by function name, with the `commit` and the UTC `date` that `git blame` gives the line that declares the function (`APS5_VABI name(`, whitespace changes ignored). It needs a git work tree and fails with a usage error otherwise, so the scanner still runs on a plain archive without the flag. A blame names the commit that last wrote the declaration line, so a later edit of that line moves the origin; a shallow clone attributes older lines to its boundary commit. The Pages workflows use it with the full history; the pull request report uses it on the merged tree.
- Provenance of an observation. Each NID line of a manifest ends with a tag: `audit: <tool> <date>`, `loader` or `manual: <reason>`. The scan records the tag of every observed stub in the group's `observed_tags`, and the library totals count them in `observed_by_tag`; the page lists the counts. `observed_imports.py add` writes `audit: import_audit <date>` (`--tool audit_dump` and `--date` change it), `entry` requires `--tag` (and `--reason` for `manual`), and `check` rejects an unknown tag and lists the untagged entries. The `observed-manifest` convention rule rejects unknown tags in a pull request and `observed-untagged` warns about untagged lines it adds.
- Inventory source. `docs/dev/inventory/<library>.txt` lists `<NID>  <source>` per line (sorted, no repeats, `#` comments allowed), where the source is the name of the firmware NID list the stub was generated from. `tools/stubgen.py --inventory-source NAME --inventory-out docs/dev/inventory/<library>.txt` writes it next to the generated code and keeps the sources already there. The scan records the source of each pending function in the group's `inventory`; the `inventory-manifest` convention rule validates the files. No listing is shipped yet, so the field appears only once one is added.

The map shows them: when any of these records exists, the site also gets `progress-detail.svg`, linked from the progress page (the plain `progress.svg` keeps only the tooltip of each library, so it stays small enough for the README). In the detailed map the tooltip of each pending cell names the function, whether it is observed (and by which tag) or unobserved, the commit and date of its declaration, and its inventory source. The pull request report lists each newly declared stub with a link to its origin commit.

## History

[`tools/progress_history.py`](../../tools/progress_history.py) measures the first-parent history of `main` with the same rules as `progress.py` and writes `history.json`, `history.svg` and `history.html` (the chart with a tooltip per day plus a table, linked from the README and the end of the progress page). The chart plots counts, not percentages, so it shows how much is added over time: one panel for library functions and one for shader instructions, each on its own scale with the implemented count as a solid line and the declared total as a dashed one (for shaders the declared total is the instruction list in `tools/rdna_isa.txt`); the current percentage sits next to each panel's implemented label. It takes one point per UTC day, at the last commit of the day, and skips commits whose tree lacks the scanned paths. The chart compacts as days accumulate: up to 14 days it labels every day, up to 150 days one label per Monday, beyond that one per month; points are drawn up to 45 days, and every day keeps a hover tooltip, while the table and `history.json` keep every day. Old trees are measured with today's counting rules and instruction list, so the series is comparable but not what the page showed on that day. It plots the counted total, implemented functions plus observed stubs, the figure the percentage uses. A commit measures `docs/dev/observed` as it was at that commit, and commits from before the manifests have none, so their stubs are all unobserved and their counted figure is only the implemented functions plus the observed stubs the manifests of that commit name. Each point is measured at its own commit, so adding a manifest changes only the points after it. The workflow checks out the full history for it.

Each point keeps the observed and unobserved split (`libraries.unobserved` and `libraries.declared_total` in `history.json`, next to `done`, `total` and `percent`) and the sha of the commit it was measured at. Points measured before this field existed have neither and are drawn with no unobserved stubs. The chart adds an observed-stubs line (red) and an unobserved-stubs line (grey) to the library panel, with their own labels and tooltip numbers, and the table gives the commit of each day as a link plus how many functions were declared since the previous day, so a jump in stubs points at the commit that added them. The per-commit cache accepts both record shapes.

## Comparisons

Comparisons identify functions by library and name. When a head group becomes a shared-source wrapper, its previous definitions are compared under the source library's identity. Removing a duplicate implementation is reported as sharing sources, without reporting the retained functions as removed.

Real removals and transitions back to stubs remain visible. Percentages retain the original snapshot totals, so eliminating duplicate accounting can change a percentage without changing available functionality. Older JSON snapshots without `shared_sources`, `unobserved` or `classified` are accepted, and their stubs are all observed.

PR reports include a table of changed libraries with implemented export counts, declared totals, percentages before and after, and the change in percent (`%`), the difference between the two percentages, written with the same unit as the headline of the report. The table uses the same two JSON snapshots as the global report, and shows `+N unobserved` next to a library's counts when it has unobserved stubs; a library whose stubs are all unobserved shows `0/0 observed`. New stubs are listed as observed or unobserved, with their own counts in the headline. When the number of unobserved stubs changes, the headline also gives the declared percentage before and after (`declared 33.33% → 25.0%`), because the headline percentage does not move for an unobserved stub. A library appears when its counts, export names or shared-source owner change, including when its counts stay equal. Unchanged libraries are omitted, and the table lists at most 100 libraries in name order with a count of omitted rows.

New or removed libraries show `Not present` on the missing side. Libraries whose snapshots contain both counts and report zero exports show `No exports`; if either count is absent, the table shows `Counts unavailable`. Wrappers show `Shared sources` with the source library's name. These rows show `n/a` for the percentage change. The table retains the scanner's counting rules; it does not measure compatibility.

Implemented definitions are also classified as behaviourally empty when their body holds only `(void)name;` discards and at most one constant return, bare `return;` or `throw`, including a return of a local wrapper that is itself behaviourally empty; wrapper calls whose arguments contain calls do not qualify. Comparisons list newly implemented behaviourally empty functions without changing any count. A separate list names newly implemented functions that no manifest of a classified library names. Older JSON snapshots without `inert_names` are accepted.

## One library

`--module NAME` limits the library totals to those directories under `core/libs/prx`. Repeat the flag to include several. A name that is not a directory is an error. Shader counts stay complete. A shared-source wrapper is included only when its own directory is named. `--json` prints the object written to `progress.json` on stdout, instead of the two summary lines. The libraries line adds the declared percentage and the number of unobserved stubs when there are any. Either flag makes the output directory optional. Without them the directory is still required, and a run that names only the directory still writes the whole tree.

## Verification

```sh
python3 tools/tests/test_progress.py
python3 tools/progress.py /tmp/anyps5-progress
python3 tools/progress.py --module libScePad
python3 tools/progress.py --json
python3 tools/tests/test_progress_history.py
python3 tools/tests/test_observed_imports.py
python3 tools/tests/test_check_conventions_observed.py
python3 tools/tests/test_stub_origins.py
python3 tools/progress.py --origins --json --module libScePad
python3 tools/observed_imports.py check
```

The regressions check that adding test callbacks leaves counts and comparisons unchanged, including when a callback shares a pending function's name or a wrapper uses shared sources. They also create a source library and a copied wrapper, move the wrapper to a shared builder, check output labels and totals, then verify real regressions and removals are still reported. The observed-state tests check each state with and without the NID in the manifest, a library with no manifest (all its pending stubs unobserved), an empty manifest, aliases and old snapshots. With `BUILD_TESTING=ON` and Python available, CTest registers them as `progress_report`, `observed_imports`, `stub_origins` and `conventions_observed`.
