- [sceGnmIsUserPaEnabled, sceGnmDriverCaptureInProgress, sceRazorIsLoaded](../../../core/libs/prx/libSceGnmDriver/Export.cpp) (libSceGnmDriver, PS4) - return false: the user performance analysis mode, GPU captures, driver traces and the Razor GPU profiler belong to development tools and are not present, as shadPS4 also answers for retail firmware. ### Functional

- [NeoMode-only imports](../../../core/libs/prx/libSceGnmDriver/Export.cpp) (libSceGnmDriver, PS4) - the 19 imports inFAMOUS Second Son asks of `libSceGnmDriver` that only `libSceGnmDriverForNeoMode` exported are now exported here too: `sceGnmSetEmbeddedPsShader` and `sceGnmSetEmbeddedVsShader` reuse the same embedded shader producers, and the other 17 throw `NotImplemented_nid_no_patch` until their console behavior is measured (#17581).
- [Packet types](../../../core/libs/prx/libSceGnmDriver/Export.cpp) (libSceGnmDriver, PS4) - on the PS4 Gnm path a type-0 packet (a register write by base index and count) or a type-1 packet in a draw or constant command buffer throws with its type, header and dword position; neither is applied, because no title has shown what a type-0 payload carries here, and the AGC driver (PM4 type-0 packets in [libSceAgcDriver.md](libSceAgcDriver.md)) rejects them too. Seen in CUSA04865, which produces a header dword of 1 itself: its compute dispatch, through a 16-byte V# over an 8-byte `allocateFromCommandBuffer` block, stores 1 over the next packet's header after the title has rebuilt the buffer for the next frame, while the queue trails the title by several milliseconds; the message gives the header and position only, since a dword of 1 is also a valid type-0 write in general, and `APS5_GNM_SUBMIT_WAIT_IDLE=1` (Submission pacing, below) keeps the queue ahead of it.
- [Workload streams](../../../core/libs/prx/libSceGnmDriver/Export.cpp) (libSceGnmDriver, PS4) - not measured on a console, and no stream or workload is recorded: `sceGnmCreateWorkloadStream` always hands out stream 1, `sceGnmBeginWorkload` workload 1, and `sceGnmEndWorkload` accepts values no call returned. The results follow [shadPS4](https://github.com/shadps4-emu/shadPS4/blob/f46a693c802f2d60573e07927b5fdaa753136567/src/core/libraries/gnmdriver/gnmdriver.cpp) (PS4; lines 168, 215 and 918), which keeps no state either: create returns 3 for a null name or output; begin 3 for a null output, checked before the stream, and 1 with workload 0 for a stream of 16 or more; end 2 for workload 0 or a top byte of 16 or more. It does not settle stream 0, how the console numbers streams and workloads, or PS5 firmware. `sceGnmGetOffChipTessellationBufferSize` returns its `0x800000` (line 1000), also unmeasured. [libSceGnmDriverForNeoMode](libSceGnmDriverForNeoMode.md) answers the same.
- [Submission pacing](../../../core/libs/prx/libSceGnmDriver/Export.cpp) (libSceGnmDriver, PS4) - a submission is queued without waiting for earlier ones, so the GPU can trail the title by several milliseconds, far more than the console's command processor. A title that reuses command buffer memory or descriptor tables a frame later then races with work that has not run yet: CUSA04865 loses packet headers and binds descriptors from rebuilt tables. `APS5_GNM_SUBMIT_WAIT_IDLE=1` waits for all queued work before each `sceGnmSubmitCommandBuffers` and `sceGnmSubmitAndFlipCommandBuffers` that follows an earlier one, across `sceGnmSubmitDone` as well, so the GPU trails the title by at most one submission, which removes these races there; it is off by default because a submission whose packets wait on a label the title writes only after a later submission would never finish. The wait holds the submission lock, so a label written by another thread after it takes that lock hangs the same way.

- [Shared dispatch and shader register writers](../../../core/libs/prx/libSceGnmDriver/include/CommandWriters.hpp) - console packets and refusals are unmeasured. The ten mode-independent writers share the Neo provider's implementation, following [shadPS4](https://github.com/shadps4-emu/shadPS4/blob/a808e7626e3c7de8d0f0fda6a91f620b42f6c762/src/core/libraries/gnmdriver/gnmdriver.cpp). The normal wrappers use `_nid_disambig1` to retain guest NIDs without colliding with Neo host symbols; both providers' pinned PS5 3.20 export tables list the names. Other imports of [#17581](https://github.com/boykopovar/AnyPS5/issues/17581), including mode-dependent draws, VGT and default-state writers, remain absent; a title loading these shared writers is not evidence that it can start.
- [sceGnmUpdateHsShader](../../../core/libs/prx/libSceGnmDriver/include/CommandWriters.hpp) (normal and Neo providers) - preserves upstream acceptance of a 29-dword (`0x1d`) reservation and guarded copy of 29 dwords. The unchanged packets declare 30 dwords: 18 words followed by a NOP with 11 payload words plus its header. A following command at word 29 is therefore treated as NOP payload, even though the host copy leaves it untouched. Console reservation sizes and the correct trailing NOP length are unmeasured; this refactor deliberately changes neither the guest size contract nor the packet encoding. `GuestGnmSharedWriters.cpp` records the inherited mismatch for both providers, not a valid packet boundary. Closes when: console measurements establish the reservation and packet extent and a separate behavior fix is validated against them.
