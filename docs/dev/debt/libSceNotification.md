# libSceNotification technical debt

### Silent stubs

- [sceNotificationHidePsButtonPersistentBanner](../../../core/libs/prx/libSceNotification/Export.cpp) (libSceNotification) - AnyPS5 has no system UI, so no persistent banner is ever shown and there is nothing to hide; the call returns without effect. When a system UI appears, this must clear the banner `sceNotificationShowPsButtonPersistentBanner` put up.

### Functional

- [the send calls and the banner](../../../core/libs/prx/libSceNotification/Export.cpp) (libSceNotification) - the gap: nothing is displayed, because AnyPS5 has no notification service or system UI. Signatures, the 0x1800-byte message limit, the 0x20-byte id limit and the 0x81980001 answer for a bad or empty message follow [SharpProspero](https://github.com/SvenGDK/SharpProspero/blob/5dfdb4b0b166e83dc9ae275001afb695f12c7174/src/SharpProspero/Interop/Notification/SceNotification.cs); a null or empty id or JSON body is answered with the same code, as that summary names no per-argument code, a null banner configuration is the documented empty configuration, and the success return follows the platform's 0 convention, which the summary does not spell out. The send calls and the banner show log what they would show, as the kernel request path `sceKernelSendNotificationRequest` does. When a notification service appears, these must hand it the message.
- [the NUL accounting of the limits](../../../core/libs/prx/libSceNotification/Export.cpp) (libSceNotification) - whether the 0x1800-byte message limit and the 0x20-byte id limit include the terminating NUL is not established: the SharpProspero summary says only "up to" that many bytes. AnyPS5 counts characters before the NUL, so the full 0x1800 characters plus the NUL are accepted. It reads at most `MessageCapacity + 1` or `IdCapacity + 1` bytes through checked guest access; an unreadable non-null pointer returns the existing invalid-message code as a host-safety fallback. The console's invalid-memory behavior is unmeasured. The banner's separate raw string logging remains unchanged.
