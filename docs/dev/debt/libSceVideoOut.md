# libSceVideoOut technical debt

### Silent stubs

- [sceVideoOutOpen](../../../core/libs/prx/libSceVideoOut/src/Output.cpp) validates the priority and CPU affinity that the open param requests for the VideoOut service thread but does not apply them: the port's present and vblank threads are host threads, and guest priorities and affinities do not reach host scheduling. Of the 16 calls in ten titles checked, all pass user 255 and index 0, 13 pass bus type 0 and three read it from a field (one call each in Borderlands 4, MXGP 26 and Super Meat Boy 3D), and 13 pass no open param. Metal Gear Solid 4 (PPSA18194) passes one from `mgs4.elf` with neither flag set and one from its launcher that sets only the affinity, 0x3e. Astro Bot (PPSA21564) sets priority 256 and affinity 0x1fff
- [sceVideoOutLatencyControlWaitBeforeInput, sceVideoOutLatencyMeasureSetStartPoint](../../../core/libs/prx/libSceVideoOut/src/Output.cpp) (libSceVideoOut) - check the handle and return 0, and an unopened handle throws `VIDEO_OUT_ERROR_INVALID_HANDLE`. The wait-before-input call waits for nothing and the start point is not recorded: the host output keeps no latency measurement to wait on or start. PPSA34502 calls each once. What the console waits for, and what it measures from the start point, is not measured
- [sceVideoOutAddVrrStatusFlagsPrivilege](../../../core/libs/prx/libSceVideoOut/src/Output.cpp) returns 0 and does nothing: the host output has no VRR state to report. The name comes from an assert message in a title that requires `SCE_VIDEO_OUT_OK`; the NID hashes to it, the arguments are unknown (it is called without any)
- [sceVideoOutVrrPegToFixedRate, sceVideoOutVrrUnpegFromFixedRate](../../../core/libs/prx/libSceVideoOut/src/Output.cpp) (libSceVideoOut) - PPSA05684 passes the handle to both, two further zero arguments to `sceVideoOutVrrPegToFixedRate`, and ignores the results. The meaning of those two arguments is unknown, so only zeros are accepted. VRR is not modelled and the output always runs at a fixed rate, so both calls only validate the handle and return 0. Every direct call in the titles checked passes the constant 0 for both the second and the third argument; the value in titles that reach the function only through a tail jump is not known. A PS5 (firmware 11.60, payload process) returned 0x8029000b for handle -1 in both calls (with zeros for the other arguments), which is returned here without looking at the arguments; a handle that is not -1 but not open, and non-zero arguments, are unmeasured and still throw. For a valid handle the same process returned 0x8029001c in all seven cases tried (three of them also printed "System processes should use sceVideoOutSysSetDrrPeg() instead"), so the title-process result is not measured and is not modelled
- [sceVideoOutCursorSet2xMagnify](../../../core/libs/prx/libSceVideoOut/src/Output.cpp) takes the handle and the cursor index like the other cursor calls and returns 0: no cursor image is drawn, so a magnified cursor cannot be observed, and the console's answer is unmeasured. PC5 (PPSA11018) imports it. The signature `(handle, index, enable)` and the effect of the flag are unverified
- [sceVideoOutSetWindowModeMargins](../../../core/libs/prx/libSceVideoOut/src/Output.cpp) (libSceVideoOut) - checks the handle and returns 0 without applying `top` or `bottom`, so the output pane always covers the full size (see `sceVideoOutGetResolutionStatus` below). Of the 38 titles relinked here, four call it once each: Borderlands 4 (PPSA01494), Metal Gear Solid 4 (PPSA18194), MXGP 26 (PPSA30839) and Super Meat Boy 3D (PPSA31162). All four pass the handle from a structure field and margins computed at run time (truncated from float values), so the margins they ask for are not known from the code alone

It is not multitouch, has no inertia after release, and does not follow the cursor outside the window. A real touchpad's finger timing and pressure are not modelled.

### Mouse gyro gaps

- [KeyboardMouse](../../../core/libs/prx/libSceVideoOut/src/KeyboardMouse.cpp) - `ANYPS5_MOUSE_GYRO=1` maps captured mouse movement to gyro rates with a fixed scale of 0.001 rad per count; the scale is not calibrated against a real controller, and the accelerometer stays at rest.
### Host input mapping gaps

- [PadInput](../../../core/libs/prx/libSceVideoOut/src/PadInput.cpp) - a `PAD:` chord fires its emulator action and its buttons still reach the title's pad state. Masking the chord buttons while the chord is held is not done, so a chord that uses a button the title needs also reaches the title.
- [PadInput](../../../core/libs/prx/libSceVideoOut/src/PadInput.cpp) - `PAD:` chords are evaluated on controller button events only and are not dispatched while the IME or a modal dialog captures input.
### Host input mapping gaps

- [InputMapping](../../../core/libs/prx/libSceVideoOut/src/InputMapping.cpp) - the file watch compares modification time and size, so a rewrite that keeps both is not seen; the stamp is taken when the watch thread starts, so a change made between the initial load and that start is not reloaded until the next change.
