### Functional

- [sceHttpCacheSystemInit and sceHttpCacheSystemClearAll](../../../core/libs/prx/libSceHttpCache/Export.cpp) - the wrappers at `0x2d570` and `0x2d680` in the 11.00 system module `libSceHttpCache.sprx` (SHA-256 `0d825d639b642a73b3ae7d7e0217f602104609d388cf8e0ae83ba50a8a2c2fd1`) validate a non-null path of at most 0x400 bytes, return `0x817a0012` on failure, pass it to their delegate and return 0 without checking its result. `SystemInit` validates the copied path and returns 0 without storing it. `SystemClearAll` validates and then throws through `NotImplemented_nid_no_patch`, because the delegate's effect on the per-application caches is not established. The host copies it once through `CopyGuestString_nid_no_patch`, so an invalid pointer or an unterminated string across an unreadable page returns `0x817a0012` instead of faulting. The wrappers' path conversion is not reproduced, so non-ASCII or invalid UTF-8 paths may be accepted, and the console's on-disk layout is not modelled. `SystemShutdown`, `SystemTerm` and `SystemSendStatistics` return 0 as their wrappers do.

- [libSceHttpCache](../../../core/libs/prx/libSceHttpCache/Export.cpp) - cached responses live in process memory, keyed by user, URL and `User-Agent` value, instead of the console's per-user files, so they are lost when the process exits; they survive `Term`. Request states, freshness, revalidation and header rules follow firmware 13.60, read from disassembly, not measured on a console. A `public` response stored while cache sharing is on, which the console files under the store shared by all users, throws through `NotImplemented_nid_no_patch`, as do a lookup and a `ClearAll` by another user while such an entry exists, since whether they reach the shared store was not read. The console's debug request header that adds cache state to responses is not reproduced. Header numbers the firmware's `stoul` or `stol` rejects, a null URL in `Retrieve` (the firmware dereferences it) and an empty header list to return throw.
- [libSceHttpCache](../../../core/libs/prx/libSceHttpCache/Export.cpp) - `SetQuota` and a non-null `RegisterCacheInfoUrl` throw through `NotImplemented_nid_no_patch` once their arguments pass; `RemoveTag`, `ClearCacheInfo` and both `WithMemoryPool` forms have unresolved signatures and throw outright. Cached entries carry the tag of the request that stored them: `CreateRequestWithTag` records a tag of up to 31 bytes with the same user and cache checks as `CreateRequest`, and rejects a null, empty or longer tag with `0x817a0012`; `Clear` erases the stored entries of one user that carry the same tag, and `ClearAllUserTags` erases every tagged entry of the listed users while untagged entries survive. A null, empty or longer tag is `0x817a0012`, an unknown cache is `0x817a0011`, and a system or unregistered user clears nothing and succeeds, as `ClearAll` does. Whether the console keys a tag to a user, replaces a tag on a later store of the same key, or rejects tags at these lengths has not been measured; the tag lifetime is this host's choice. `Init` ignores its pool size, so the pool allocation failure is not reproduced, and storing never fails, so the console's file errors are not reproduced.
- [libSceHttpCache](../../../core/libs/prx/libSceHttpCache/Export.cpp) - the freshness lifetime is `Expires` minus `Date`, or a tenth of `Date` minus `Last-Modified`, computed on unsigned ticks without comparing them first, and an entry is fresh while its age is below that lifetime, as in firmware 13.60, read from disassembly, not measured on a console. An `Expires` earlier than `Date`, or a `Last-Modified` later than `Date`, therefore wraps to a lifetime that never runs out, so the entry keeps being returned as a hit instead of going stale as RFC 9111 asks; this is kept to match the console.
