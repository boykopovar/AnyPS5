  - The bundled `libScePsml.sprx` (PPSA13197) computes the shared requirement differently: `{0x200000, 0x200000, local}` where `local = ceil(table[type]/0x200000) + (table[type] + (type==1 ? 0x40000000 : 0x10000000) < 0x200000 ? 3 : 0)` and `table` is three u64s `{0x7C00000000, 0x100000000, 0x8A6C003E00000004}` at VA `0x6cc28`, loaded with `movsxd r13, dword ptr [rsi]` (`0x28e21`, the parameter's first dword) and `mov r15, qword ptr [rax + r13*8]` (`0x28e35`). Type 0 yields 0x3E000 blocks (about 496 GiB) versus the 52 measured on a 13.40 console; the contradiction is unresolved (different module revision or a different parameter layout), so the console-measured 52 is kept for type 0 and types 1 and 2 still throw. `scePsmlMfsrCreateSharedResources` demands the same 52 blocks; the bundled create body is version-gated (SDK 0x11000000) and undecoded.
  - The context requirement reports four 2 MiB blocks regardless of its parameters, while the system calculation depends on the context configuration. The descriptor pointer at 0x28 is not read. Validation throws for null pointers, short block lists and foreign handles instead of reproducing the system error and fault behaviour.

- [scePsmlMfsrGetDispatchMfsrPacket1000](../../../core/libs/prx/libScePsml_debug/Export.cpp) (libScePsml) - imported by PPSA25344. libScePsml and libScePsml_debug are built from the same source. The bundled module copies the 0x158-byte parameter into a 0x1D8-byte dispatch descriptor (forcing +0x134 = 1.0f, +0x148/+0x40 = 0, masking +0x120 with 0x80018000, zeroing +0x128 when context byte +0x1A8C bit 0 is clear plus +0x158, +0x15C, +0x160..+0x1A4 and +0x1A8) and submits it to the shared writer: uninitialized returns 0x8A810001, an engine id other than 0xA9C4/0x9231 returns 0x8A810005, a null command buffer returns 0x8A810009, and a module-state flag combination returns 0x8A810016. Its AGC packet emission into the command buffer (ring slots at context +0x4A8, PM4 writes at 0x4E0) is not implemented and throws; the validation that precedes it is ported.
  - the `0x8A810016` combination: module-global `0x16ec10` (written at `0x2a6fe` from bit 30 of the module's own parameter dword by the one-time init routine `0x2a660`) clear while module-global `0x16ec39` (set at `0x2e01f` by a VideoOut mode-event handler from `sceVideoOutGetPipelineStatus` field +0 == 1) is set, with a pending-submission counter that is an always-zero helper in this build. The `param` argument is not inspected before emission — it only feeds the descriptor copy — so no caller input reaches the error: both flags are unmodeled (module parameters are not processed and the VideoOut pipeline status is unimplemented), `g_mfsrLowLatencySubmit` and `g_mfsrSyncSubmit` default false, and the whole path is unreachable while `sceKernelIsTrinityMode` returns 0.

- [scePsmlMfsrInit](../../../core/libs/prx/libScePsml_debug/Export.cpp) (libScePsml) - mirrors the bundled `libScePsml.sprx` (PPSA13197) and the console library: it logs the release banner, then returns 0x8A810012 when `sceKernelIsTrinityMode` returns 0 — ahead of the initialized-state check, so repeated calls also return 0x8A810012 — and every later MFSR call returns 0x8A810001.
  - On a Trinity console the module then probes AGC capability (0x8A810010 on failure), registers its dispatch components (0x8A810011), starts a worker and sets the initialized flag, after which a repeated call returns 0x8A810002. The model deliberately throws past the console check rather than fabricate the probe, registration, worker and flag — every MFSR call after a partial init would act as if the engine existed. AnyPS5 reports 0 for `sceKernelIsTrinityMode`, so this stays unreachable until that changes. PPSA08330 calls the setup unconditionally and only uses a context when its cached `sceKernelIsTrinityMode` result is set (0x3c643d, 0x567f97; otherwise it stores a -0.25 mip bias itself at 0x567fe2)
