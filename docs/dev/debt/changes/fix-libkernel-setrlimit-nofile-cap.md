# libkernel

## change [setrlimit](../../../core/libs/prx/libkernel/System/src/Process.cpp)

- [setrlimit](../../../core/libs/prx/libkernel/System/src/Process.cpp) (libkernel) validates the resource and input in FreeBSD order, maps negative limits to infinity, and lowers a soft limit above the hard limit. A request other than `RLIMIT_CORE`, `RLIMIT_NPROC` and `RLIMIT_NOFILE` succeeds when its normalized values match `getrlimit`; `RLIMIT_NOFILE` stores the normalized guest limits after clamping the hard limit to the measured per-process ceiling 12555 and then clamping the soft limit to that hard limit. Descriptor allocation still follows the host: neither a lowered guest soft limit nor a guest limit raised above the host's capacity is enforced; on Windows, after the guest-visible limit was raised to 12555, a pipe-descriptor probe still reached `EMFILE` after 8188 descriptors. `RLIMIT_CORE` stores a soft limit with the hard limit unchanged and enforces nothing, as AnyPS5 writes no core file. A raised `RLIMIT_DATA` or `RLIMIT_STACK` hard limit with the soft limit unchanged returns 0 and keeps both limits. Changing other limits throws because guest limit state is not stored. In a payload process on a PS5 (firmware 12.70), `setrlimit(RLIMIT_NOFILE)` changes {1000, 13952} to {1000, 12555} and changes {13952, 13952} to {12555, 12555}; here those requests are clamped the same way instead of being rejected when the requested hard limit exceeds the host-derived current limit. Setting `RLIMIT_STACK`, `RLIMIT_RSS` and `RLIMIT_MEMLOCK` to their current values succeeds and changes nothing, as here; a raised `RLIMIT_DATA` or `RLIMIT_STACK` hard limit (+1, x2, +2^32, infinity) with the soft limit unchanged returns 0 and changes nothing, as here, and a changed soft limit of those two together with a raised hard limit is unmeasured and throws here; `RLIMIT_CORE` soft limits 0, 4096 and infinity read back, and {2, 1}, normalised to {1, 1}, returns 0 and is not read back; setting `RLIMIT_NPROC` to its current 1604 also succeeds but leaves 1443. `RLIMIT_NPROC` follows FreeBSD 11 by clamping both values to 1 through `maxprocperuid`, stores the result and returns it from `getrlimit`. The initial 1604 and `maxprocperuid` 1443 follow that measurement: process 0's limit starts at `maxproc` ([`init_main.c`](https://github.com/freebsd/freebsd-src/blob/release/11.0.0/sys/kern/init_main.c#L550-L551)), `maxprocperuid` starts at nine tenths of it ([`subr_param.c`](https://github.com/freebsd/freebsd-src/blob/release/11.0.0/sys/kern/subr_param.c#L258)), and `setrlimit` applies that bound ([`kern_resource.c`](https://github.com/freebsd/freebsd-src/blob/release/11.0.0/sys/kern/kern_resource.c#L714-L718)). `kern.maxproc` fails with `ENOENT` in the payload process, so the values cannot be queried independently, and process creation does not enforce the stored limit. Java 25 LAN / DNS (PPSA99869) sets `rlim_cur = MIN(0x100000, rlim_max)` during VM initialization
