# libSceLibreSsl3
## change [AES_wrap_key]
- [AES_wrap_key](../../../core/libs/prx/libSceLibreSsl3/src/AesWrap.cpp) - follows [RFC 3394](https://www.rfc-editor.org/rfc/rfc3394) with the default IV `A6A6A6A6A6A6A6A6`, six rounds and the 64-bit counter XORed into the A block; it encrypts through libSceLibreSsl's `AES_encrypt`. Inputs below 16 bytes or not a multiple of 8 return -1 as LibreSSL does (OpenSSL 1.1 returns 0); null key, input or output throws where LibreSSL dereferences it. A PS5 (firmware 11.60, payload process; a title process may differ) returned the RFC 3394 ciphertexts of sections 4.1, 4.3 and 4.6 (24, 24 and 40 bytes) for a null IV, the same bytes for an explicit `A6A6A6A6A6A6A6A6` IV and different bytes for a zero IV, -1 for the lengths 8, 15, 17 and 0, and 32 for 24; the export is in `libSceLibreSsl3.sprx` and not in `libSceLibreSsl.sprx`. Null pointers and other lengths are not measured.
## change [AES_unwrap_key]
- [AES_unwrap_key](../../../core/libs/prx/libSceLibreSsl3/src/Aes.cpp) (libSceLibreSsl3) - A PS5 (firmware 11.60, payload process; a title process may differ) unwrapped the RFC 3394 section 4.1 ciphertext to 16 bytes with the original key data and returned 0 for the same ciphertext with its last byte changed (the output bytes after that failure were not read); other lengths and null pointers are not measured. The name comes only from the `tools/nid_names.py` hash of the 13.60 table entry `JvoQz7GYOMo`. The prototype and behaviour follow [LibreSSL 4.0.0](https://github.com/libressl/openbsd/blob/ce488b78e0bd994780569df718596b9776ff681a/src/lib/libcrypto/aes/aes.c) `aes.c` (3.8.4 `aes_wrap.c` has the same body): an RFC 3394 unwrap through libSceLibreSsl's `AES_decrypt`. A length that is not a multiple of 8 or is under 24 returns -1, an integrity mismatch zeroes the `inlen - 8` output bytes and returns 0, and a null `iv` uses the default IV. A null key, input or output, which LibreSSL dereferences, throws.
