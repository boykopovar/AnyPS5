# libkernel

## change [sceKernelDirectMemoryQuery]

- [sceKernelDirectMemoryQuery](../../../core/libs/prx/libkernel/DirectMemory/Export.cpp) (libkernel) - follows a payload process on firmware 13.00, which tried every single flag bit at the start of a block, in a released range before another block, and at 0x4fff00000, in a gap below the block at 0x1000000000. Bits 1 to 27 are ignored: each returns the block as flags 0 do, or EACCES where no block is found, and with bit 0 (find-next) the next block, measured for flags 3, 5, 9, 0x11, 0x201, 0x1001 and 0x10001. Bit 28 alone returns EINVAL in all three places. Bit 30, alone or with bit 1, returns EINVAL on a block and EACCES where no block is found, writing nothing. Bits 29 and 31, alone or together with bit 30, return EACCES where no block is found; on a block they return 0 and write another record (bit 29 eight bytes, its value 0x454630000; bit 31 and 0xc0000000 24 bytes, the first field 0x200000064 here and 0x200000056 or 0x200000057 in earlier runs), so they throw there. A negative offset (-1 and -0x10000) returns EACCES for flags 0, bit 30 and bit 31; with bit 0 it returned the block at 0x1000000000, which this does not model, so that throws. A size of 0 returns 0 and writes nothing; 16 writes 16 bytes and 32 writes the 24-byte record. On system software 12.40 [obSCEne measured](https://github.com/project-oops/obSCEne/blob/de5efc406319ade18df00654025494804405a7fb/reports/hardware/report-20261013-172400.log#L11881-L11947) EINVAL for flags 2 and 4, so the answer depends on the firmware, which is not modeled. Unmeasured, and throwing: bit 28 with any other bit; bit 0 with bits 28 to 31 (0x40000001 returned EINVAL in the released range but a 16-byte record in the gap); bit 29 with bit 30 or 31; a size of 0 where no block is found. Unmeasured, and answered like the measured bits: combinations of bits 1 to 27 other than those listed, bit 30 with bits 2 to 27, and bits 29 to 31 with bits 1 to 27. Not measured for PS4 titles.
