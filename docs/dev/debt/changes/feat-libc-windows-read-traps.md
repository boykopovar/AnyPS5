# libc

## add Functional

- On Windows the [write watch](../../../core/libs/prx/libc/src/GuestWriteWatch.cpp) read traps (`GuestWriteWatchTrapReads`) make pages `PAGE_NOACCESS` with `VirtualProtect` and are resolved from a vectored exception handler added first in the chain with the first resolver, which passes other faults on; no library sets them yet. They share the gaps of the Linux read traps: a system call that reads a trapped page fails instead of faulting, a resolver that stores into its range with the CPU makes each page accessible to every thread at its first store there, and a thread that holds what the resolver needs and touches a trapped range waits forever. In addition:
  - a trap is set only on committed guest arena pages that `VirtualQuery` reports as exactly `PAGE_READWRITE` and that lie in [resident runs](../../../core/libs/prx/libc/include/WindowsMappings.hpp): shared views and views demoted for an alias are refused, since write tracking and eviction change their protection themselves. A `VirtualProtect` outside the guest arena and libkernel's `mprotect` is not seen, and a trap released there gives the page back read-write;
  - the guest arena's commit, reset and mappings and libkernel's `mprotect` resolve the traps over their range, widened to the resident runs it touches, before changing it, and no trap is set there while they run. An alias of a resident run (`GuestArenaMapAlias`) drops the traps in the run without running the resolver, since a host import makes it under the write tracker lock the resolver takes; the drop shows in `GuestWriteWatchReadTrapGeneration`, and a read before the caller stores the range sees the bytes from before the trap.
