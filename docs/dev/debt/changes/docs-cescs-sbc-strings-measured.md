# libSceCesCs
## change [UTF-16 and UTF-32 forms of the single-byte and MBCS string conversions]
- [UTF-16 and UTF-32 forms of the single-byte and MBCS string conversions](../../../core/libs/prx/libSceCesCs/Export.cpp) (libSceCesCs) - errors, their precedence and the optional length pointers of `sceCesSbcTo{Ucs2,Utf16,Utf32}*`, `sceCes{Ucs2,Utf16,Utf32}*ToSbc`, `sceCesMbcsStr{To,Get}{Utf16,Utf32}*` and `sceCes{Utf16,Utf32}Str{To,Get}Mbcs*` are unverified against the console except as measured below. Signatures follow the Orbital type database linked above. They follow `sceCesSbcToUtf8`, `sceCesUtf8ToSbc` and the UTF-8 MBCS string forms with the profiles and tables listed above. A value above U+10FFFF answers `INVALID_ENCODE`; for a surrogate `sceCesUtf32ToSbc` answers `ILLEGAL_CODE`, `sceCesUtf16ToSbc` a lone high one `SRC_BUFFER_END` and a lone low one `INVALID_ENCODE`, and `sceCesUcs2ToSbc` `INVALID_ENCODE`. A valid code point no profile maps answers `UNASSIGNED_CODE`. The string forms stop at a zero code unit, write no terminator and count code units, except that `sceCesMbcsStrToUtf16Str` wrote a terminating zero on the console and writes one here, and the other string forms are unmeasured. With the Cp1252 and ISO 8859-1 profiles a PS5 (firmware 11.60, payload process; a title process may differ) agreed in 54 of 68 probed cases, among them all 256 bytes through `sceCesSbcToUcs2`, `sceCesSbcToUtf16` and `sceCesSbcToUtf32` (Cp1252 except its 5 unassigned bytes), the other single-character encoders for U+0041, U+00E9 and U+0000 with both profiles and for U+20AC and U+0152 with Cp1252, and `sceCesMbcsStrToUtf16Str` and `sceCesMbcsStrGetUtf16Len` on a string with a zero, with a terminating zero written and null length pointers accepted. It differed in 14: on an error the encoders set the output byte to 0 and `sceCesUtf16ToSbc` the length (1, or 2 for a surrogate or U+1F600) where this leaves them, `sceCesUcs2ToSbc` of U+D800 and `sceCesUtf16ToSbc` of a lone low surrogate (length 1) answered `0x805C0015` with Cp1252, Cp1254, Cp1258, ISO 8859-1 and ISO 8859-15, `sceCesSbcToUtf16` with room for 0 units answered `0x805C0031` and set length 1, the 5 unassigned Cp1252 bytes (`0x81`, `0x8D`, `0x8F`, `0x90` and `0x9D`) gave value 0 with a non-zero return, and a null profile answered `0x805C0004` with value 0 where this answers `INVALID_PARAMETER`.
## change [Single-byte profiles]
- [Single-byte profiles](../../../core/libs/prx/libSceCesCs/SingleByte.hpp) (libSceCesCs) - the console's tables for these 31 profiles are not verified, except that of ISO 8859-1, for which a PS5 (firmware 11.60, payload process; a title process may differ) returned U+0000 to U+00FF for the 256 bytes through `sceCesSbcToUcs2`, `sceCesSbcToUtf16` and `sceCesSbcToUtf32`. Each returns a profile accepted by sceCesSbcToUtf8, sceCesUtf8ToSbc and the MBCS context conversions, with bytes 0x00-0x7F unchanged and the high half of a public table: ISO 8859-1, -2, -4, -5, -9, -10, -13, -14, -15 and -16 from [unicode.org](https://unicode.org/Public/MAPPINGS/ISO8859/), code pages 437, 737, 775, 850, 852, 855, 860-864, 865 and 866 from [Microsoft's PC tables](https://unicode.org/Public/MAPPINGS/VENDORS/MICSFT/PC/), KOI8-R and KOI8-U from [unicode.org](https://unicode.org/Public/MAPPINGS/VENDORS/MISC/), and 1253, 1254, 1255, 1256, 1257 and 1258 from Microsoft's [best-fit tables](https://unicode.org/Public/MAPPINGS/VENDORS/MICSFT/WindowsBestFit/). Their unassigned bytes are in the next entry.
