# libSceConvertKeycode

## change [sceConvertKeycodeGetCharacterFromKeyboardData](../../../core/libs/prx/libSceConvertKeycode/Export.cpp): returns `0x80BC0030`

- [sceConvertKeycodeGetCharacterFromKeyboardData](../../../core/libs/prx/libSceConvertKeycode/Export.cpp): returns `0x80BC0030` for a `length` above 16 (or negative), an `led` of 8 or more, a `modifier_key` of 0x100 or more, a `state` bit outside 0x1C000080, or an index outside the key data, before the layout checks, and otherwise converts `key_code[index]` with `state | modifier_key << 8 | led << 16`. Confirmed on a PS5 Pro payload process (13.60): all five rejections answer `0x80BC0030`, in three ordered checks - key-data fields first, then the status bits, then the index - named by the module's own stderr diagnostics (`libconvkeycode.cpp` sites 825, 834 and 838); a valid record converts (keycode 4 in layout 1 gives 'a') and an invalid keyboard type propagates `0x80BC001D` from the inner conversion without writing the output. The rules were read from firmware 13.42's module run natively; they hold on a console at 13.60.

## change [sceConvertKeycodeGetCharacterFromKeyboardData](../../../core/libs/prx/libSceConvertKeycode/Export.cpp), `sceConvertKeycodeGetCharacter`,

- [sceConvertKeycodeGetCharacterFromKeyboardData](../../../core/libs/prx/libSceConvertKeycode/Export.cpp), `sceConvertKeycodeGetCharacter`, `sceConvertKeycodeGetVirtualKeycode` and `sceConvertKeycodeGetImeKeyboardType`: return `0x80BC0031` (`kErrInvalidAddress`) if guest pointers point to unmapped memory as a host-safety fallback; callers preserve `errno`. Measured on a PS5 Pro payload process (13.60) for the first three: an unwritable non-null output pointer faults the calling process in all of them - the module stores through it - so the returned code is the deviation, not the console answer; null outputs answer `0x80BC0031`, and in `sceConvertKeycodeGetCharacterFromKeyboardData` the address check runs before the record checks with an `Invalid address: keyData=... character=0` diagnostic (`libconvkeycode.cpp` site 819), while in `sceConvertKeycodeGetVirtualKeycode` the null-output check precedes the keyboard-type check (null answers `0x80BC0031` even with an invalid type). `sceConvertKeycodeGetImeKeyboardType` also answers `0x80BC0031` for a null output, and with a writable output it never returns in a payload process (keyboard types 0 and 4, two sessions) - it appears to wait on a service this environment does not provide.
