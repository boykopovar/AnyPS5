# libSceAudioIn

## change [sceAudioInHqOpen, sceAudioInAsyncOpen](../../../core/libs/prx/libSceAudioIn/Export.cpp)

- [sceAudioInHqOpen, sceAudioInAsyncOpen](../../../core/libs/prx/libSceAudioIn/Export.cpp) - PS5 wrapper validation requires 48000 Hz followed by exactly 128 samples for both calls; HqOpen then requires format 2. Measured on a PS5 Pro payload process (13.60): these three checks answer before the audio client is entered (no `_audioInOpen` trace line) - `0x80260103`, `0x80260102` and, for HqOpen with format 0, `0x80260106` - while type and index are checked inside the client (`0x80260104` and `0x80260106`) and fully valid arguments reach the service tail (which answers `0x809B0001` in this process without an audio service). The host uses the same SDL capture path for both, so native asynchronous scheduling and high-quality processing are not reproduced. Common port validation, device selection and host capture pacing remain incomplete. One title (PPSA03355, in its libfmod plugin) disassembled for this entry calls `sceAudioInAsyncOpen` from one call site (0xe5972) with index 0, 128 samples, 48000 Hz and a last argument of 2, plus a type argument of 0 or 1, which agrees with the 48000 Hz and 128 samples above; it stores the result in a slot of its own and branches on a negative result. What the last argument 2 means is not shown.

## change [sceAudioInGetHandleStatusInfo](../../../core/libs/prx/libSceAudioIn/Export.cpp) (libSceAudioIn)

- [sceAudioInGetHandleStatusInfo](../../../core/libs/prx/libSceAudioIn/Export.cpp) (libSceAudioIn) - handle gates implemented per 4.03 (handle&0x7f000000==0x30000000, index<=7, slot open). The status record layout recovered: out[0x00..0x0f] copies the entry blob at +0x80, out[0x10] is the mode snapshot stored at open, out[0x14]/out[0x18] are shm slot fields +0x402c/+0x4028, and out[0] gets bits 0x21 when +0x402c is zero. The shm service state has no host equivalent, so the export still throws past validation. Measured on a PS5 Pro payload process (13.60): the gates answer before anything is written - handle -1 gives `0x80260101` and a valid-base free slot (0x30000000) gives `0x80260109` - both leaving a sentinel-filled info buffer untouched.
