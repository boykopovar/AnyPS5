# libSceAgcDriver

## change [1_5_5_5 color targets]

- [1_5_5_5 color targets](../../../core/libs/prx/libSceAgcDriver/Graphics/src/State.cpp) (libSceAgcDriver) render into A1R5G5B5: X bits 0-4, Y 5-9, Z 10-14, W 15 ([fpPS4](https://github.com/red-prig/fpPS4) `kSurfaceFormat1_5_5_5`; packed 16-bit textures entry). STD, ALT, STD_REV, ALT_REV fill XYZW with RGBA, BGRA, ABGR, ARGB ([Mesa 26.2.2](https://gitlab.freedesktop.org/mesa/mesa/-/blob/mesa-26.2.2/src/amd/common/ac_formats.c) `ac_translate_colorswap`); shadPS4 and KytyPS5 (which names it 5_5_5_1) swap red and blue. GPU tests check texels, DCC clears and blending on the host; the export direction and which field each blend constant reaches are not measured on a PS5. UNORM only. Throw: blending other than a copy and alpha-to-coverage with STD_REV or ALT_REV, which keep alpha in X; unclamped blending, whose merge would read the R16_UINT view as float; resolves between swaps. PPSA06699 renders into it.

## change [5_6_5 color targets]

- [5_6_5 color targets](../../../core/libs/prx/libSceAgcDriver/Graphics/src/State.cpp) (libSceAgcDriver) render into R5G6B5: X bits 0-4, Y 5-10, Z 11-15. `SWAP_STD_REV` (2) writes the exports as they are and `SWAP_STD` (0) with X and Z exchanged, following `ac_translate_colorswap` in [Mesa 26.2.2 ac_formats.c](https://gitlab.freedesktop.org/mesa/mesa/-/blob/mesa-26.2.2/src/amd/common/ac_formats.c). Format, mapping and write mask are tested, and an execution test compares the texels drawn in both orders on the host device. The export direction, which field each blend constant reaches, and destination alpha reading 1 (as Vulkan defines it) are not measured on a PS5. Throw: other swaps and number types; a CB DCC decompress or eliminate of clear codes other than 0000 and a multisampled fast clear, which have no R5G6B5 encoding; unclamped blending, whose merge would read the R16_UINT view as float. PPSA27305 renders into it with `SWAP_STD_REV` (discussion #6434).

## change is a dynamic-resolution variant of another entry

- An [image table](../../../core/libs/prx/libSceAgcDriver/Graphics/src/ShaderResources.cpp) entry whose T# is a dynamic-resolution variant of another (every decoded field the same, swizzle, DCC metadata and alpha placement included, but another width, height or pitch) borrows that entry's texture: the one the newest storage write used, else the active depth surface, else the largest accessible by guest bytes, then by extent. With DCC metadata it borrows over the same key bytes, or over one key code across the wider span, proved at binding after pending key writes land; each proof of a cached set, the write index's too, needs that code again, at one scan per key change. `textureSize` and texel fetches on a borrower answer with the borrowed extent, unlike the console. A remembered table, or a cached set on its full walk, keeps its borrows only while the same entries would be chosen again; a fast proof keeps them when a depth surface becomes active over the surface without a write.

## add Functional

- [Multisampled DCC alpha placement](../../../core/libs/prx/libSceAgcDriver/Graphics/src/MultisampleTarget.cpp) (libSceAgcDriver) - a resident multisampled DCC target throws before it takes a noted metadata refill when it is bound again with another DCC alpha placement (a 1_5_5_5 target moving between STD or ALT and STD_REV or ALT_REV, or a texture owner whose T# ALPHA_IS_ON_MSB differs), or when a T# naming its DCC metadata with the other ALPHA_IS_ON_MSB samples it, reads its sample 0 or writes it as a storage image. This holds for any keys, uncompressed, 0000 and 1111 included: the target keeps no per-block keys, as draws change its image without updating the metadata, so it cannot tell which blocks still hold a 0001 or 1110 clear. How the console reads such blocks with the other placement is unknown.
- [One-channel DCC clear codes](../../../core/libs/prx/libSceAgcDriver/Graphics/src/DccMetadata.cpp) (libSceAgcDriver) - 0001 and 1110 keys over any one-channel format (R8, R16, R32 and R64, every number type) throw, whether the surface is sampled, cleared as a storage image or drawn to; converted formats stored as R32_UINT throw as converted formats. With APS5_KEYS_FILL_CLEAR=1 the throw comes when the key fill is noted, not at the next read. Mesa 26.2.2 `gfx8_get_dcc_clear_parameters` ([si_clear.c](https://gitlab.freedesktop.org/mesa/mesa/-/blob/mesa-26.2.2/src/gallium/drivers/radeonsi/si_clear.c)) takes the only channel as alpha and gives colour the same value, so it never encodes them, and the console's decode is unknown. Two-channel formats follow that function: alpha is the second channel when `ac_alpha_is_on_msb` holds and the first otherwise.
- [Variant key spans at binding](../../../core/libs/prx/libSceAgcDriver/Graphics/src/ShaderResources.cpp) (libSceAgcDriver) - the proof of a borrowed span's one key code that follows the representative's lookup has no known trigger: a storage write marks its DCC keys uncompressed when it is recorded (`StorageTexture::MarkDirty`), so the choice before the lookup already sees them, and a flush marks them only for an image whose keys still read as a clear, which no recorded write leaves behind. The proof stays, so a lookup that does change the keys cannot hand a borrower another code; `RunPendingStorageTail` in ImageTableVariants.cpp passes without it.
- [96-bit sampled textures](../../../core/libs/prx/libSceAgcDriver/Graphics/src/Texture.cpp) (libSceAgcDriver) - a sampled 32_32_32 texture is created as an optimal-tiled R32G32B32 image with transfer-destination and sampled usage, without asking the device whether it supports that format with optimal tiling. Most desktop GPUs do not, so the creation is invalid there (`VUID-VkImageCreateInfo-imageCreateMaxMipLevels-02251` on an RTX 4070). `RunZeroKeyRepresentative` in ImageTableVariants.cpp is skipped on such devices for this reason. A linear image or a conversion to R32G32B32A32 would close it.

## change [Sampled array windows]

- [Sampled array windows](../../../core/libs/prx/libSceAgcDriver/Graphics/src/TextureTiling.cpp) (libSceAgcDriver) - a sampled 2D array, 1D array or cube view past slice 0 is built from its viewed slices only (`ViewedArrayWindow`), for a thin surface without DCC metadata or whose keys all resolve to Uncompressed (the window drops the metadata). A cached set's fast proof of such a window reads no keys, so a clear written to its keys alone shows only at its next lookup. For a 64 KiB XOR swizzle the window starts at the last slice at or before the base whose swizzle slice bits are zero (R_X 1-byte and Z_X 4-byte: a multiple of 16); when that is slice 0 the view builds slices 0 to its last. A window and a whole-array view of one surface are separate images over overlapping memory, kept coherent by the overlap rules. PPSA26344 samples a cube array at slices 4299..7232 at 1467 MiB instead of about 3.8 GB; PPSA01341 samples slice 636 of a DCC 2D array at 52 MiB instead of 2.5 GiB.
