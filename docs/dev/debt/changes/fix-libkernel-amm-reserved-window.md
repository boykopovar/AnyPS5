# libkernel

## change [AMM map, map direct and unmap]

- [AMM map, map direct and unmap](../../../core/libs/prx/libkernel/Apr/src/Apr.cpp) (libSceAmpr) - signatures and protection mask from [ampr_emu](https://github.com/drakmor/ampr_emu), mapper model from [PS5PCEM](https://github.com/iStark/PS5PCEM); not confirmed on a title. The AMM ranges are the 512 GiB at 0x80000000000 that `sceKernelMapperGetParam` reports on a console ([PS5_Lichii](https://github.com/sergiolara92/PS5_Lichii), homebrew, titles not measured): the first 480 GiB the AMM range, the last 32 GiB the multimap range; the split is not measured (KytyPS5 reports an empty multimap range). Maps outside the ranges and a null `sceAmprAmmGetVirtualAddressRanges` output throw. Memory type and GPU mask are ignored, AMPR and ACP access map as CPU access, submission always returns 0, and the console's map failure and rollback are unverified

## add Functional

- [Title calls in the AMM window](../../../core/libs/prx/libkernel/DirectMemory/DirectMemory.cpp) (libkernel) - a title call that changes a range overlapping the AMM window, including one that starts in the user range, calls `NotImplemented_nid_no_patch` whether or not the host reserved the window: a fixed `mmap` or `sceKernelMmap` (anonymous or file-backed), `sceKernelMapDirectMemory`, `sceKernelMapFlexibleMemory`, `sceKernelReserveVirtualRange` or `sceKernelMemoryPoolReserve`, and `munmap`, `sceKernelMunmap`, `mprotect`, `sceKernelMprotect`, `sceKernelMtypeprotect`, `sceKernelBatchMap`, the memory pool commit, decommit and batch, `mlock`, `munlock`, `sceKernelMlock`, `sceKernelMunlock`, `sceKernelSetVirtualRangeName`, `sceKernelClearVirtualRangeName` and `sceKernelReleaseFlexibleMemory`. The console's result is not measured. A non-fixed hint inside the window is not used, like a hint above the user arena, and the mapping is placed in the user arena
- [Order of the AMM window check](../../../core/libs/prx/libkernel/DirectMemory/DirectMemory.cpp) (libkernel) - the window check runs after the checks that need no memory state: the address, length, alignment, flag and protection values, the name, and a null output pointer. An unwritable output is checked after the window: a fixed `sceKernelMemoryPoolReserve` in the window with a read-only output throws instead of returning EFAULT, and `sceKernelMmap` checks its result pointer only after it maps, so a fixed `sceKernelMmap` in the window throws with a null or invalid result pointer. Checks that read memory state are not reached, so a fixed map in the window of unallocated direct memory, or a no-overwrite map over a used range, throws instead of returning ENOMEM, and an unsupported flag throws its argument error before the direct memory is checked. The console's order is not measured
- [Release of memory the mapper maps](../../../core/libs/prx/libkernel/DirectMemory/Export.cpp) (libkernel) - `sceKernelReleaseDirectMemory` and `sceKernelCheckedReleaseDirectMemory` of direct memory with a view in the AMM window call `NotImplemented_nid_no_patch` before they unmap anything: every view, in the user arena and in the window, stays mapped and the memory stays allocated. A title that gives direct memory to the mapper and releases it while an AMM map still uses it therefore stops here; the console unmaps the mapper's view or fails the release, which is not measured
- [Release of direct memory in the AMM pool](../../../core/libs/prx/libkernel/Apr/src/Apr.cpp) (libkernel) - `sceKernelReleaseDirectMemory` and `sceKernelCheckedReleaseDirectMemory` of direct memory given to the AMM pool (`sceAmprAmmGiveDirectMemory` or `sceKernelGiveDirectMemoryToMapper` with usage 1) call `NotImplemented_nid_no_patch` before they release anything, whether or not an AMM map uses the memory, so memory given to the pool cannot be released. Memory given with usage 0 and memory never given to the mapper release normally. Whether the console takes the memory back from the pool, fails the release or leaves the pool pointing at freed memory is not measured
- [AMM window in sceKernelVirtualQuery](../../../core/libs/prx/libkernel/DirectMemory/Export.cpp) (libkernel) - `sceKernelVirtualQuery` and `sceKernelQueryMemoryProtection` report the AMM window to a title like any guest mapping: its reserved parts as one reservation and its mapped pages with their protection, and a find-next query from an address above the user arena returns the window. Whether the console reports the mapper's range to a title, and with which fields, is not measured. Closes when: measured on a PS5
- [Failure of a queued AMM command](../../../core/libs/prx/libkernel/Apr/src/Apr.cpp) (libSceAmpr) - an AMM submission returns 0 before its commands finish. The submitting thread runs the commands until one waits or the AMM queue is busy, and a command that fails there throws to the title. The rest run on the AMM queue thread, where a failing command, such as a map outside the AMM ranges or one that calls `NotImplemented_nid_no_patch`, prints the error and aborts the process after the title was told the submission succeeded. How the console reports a failing AMM command is not measured. Closes when: a failure on the queue thread is reported through the submission's completion status

# libc

## add Functional

- [AMM window address](../../../core/libs/prx/libc/include/GuestArena.hpp) (libc) - the 512 GiB AMM window is reserved at startup at a fixed host address. If the host cannot reserve it the calls below throw and name the OS error (0 on WebAssembly, which attempts none). A Linux x86-64 ThreadSanitizer build places it at 0x7E8000000000, in the high application range of compiler-rt TSan since LLVM 17; GCC libsanitizer is not checked. Under ASLR the mmap base and mappings below it can fall in the window in an estimated 1 to 3% of runs. Without the window the range query, a submission using the window and an AMM pool gift (usage 1, after its argument checks) throw; one made while the AMM queue is busy returns 0 and aborts the process when the queue thread reaches the command, per the queued AMM command entry. NOP-only submissions, building a command buffer and gifts for maps (usage 0) succeed. `guest_amm_placement` skips such a run; the other AMM tests fail. No TSan build is tested in CI
- [AMM window address space](../../../core/libs/prx/libc/src/GuestArena.cpp) (libc) - the 512 GiB AMM window is reserved at startup for every title, including one without AMM. On Linux it is a `PROT_NONE`, `MAP_NORESERVE` mapping that commits nothing but counts against `RLIMIT_AS`, on top of the about 976 GiB the guest arena reserves from 0x10000 to 0xFC00000000 outside the system-reserved range 0x7FFFFC000 to 0x1000000000, so a process needs about 1.5 TiB of address space, not 1 TiB. Under a lower limit the arena reservation fails as on the base, a limit between the two leaves the window unreserved and AMM throws, and a higher limit leaves 512 GiB less headroom for host mappings. The thresholds are approximate, as other host mappings count too. It is not reserved on first AMM use, as host mappings made while loading could take its address. Closes when: the window is reserved only for titles that use AMM, at a fixed address the host cannot take first
- [Read traps over an unmapped range](../../../core/libs/prx/libc/src/GuestWriteWatch.cpp) and [`Unmap`](../../../core/libs/prx/libkernel/DirectMemory/DirectMemory.cpp) (libc) - on Linux, unregistering a range skips read traps whose fault the resolver is handling, and the resolver then restores read-write access over the trap's pages, so a range unmapped by `sceKernelMunmap`, `munmap` or an AMM unmap while a read of it is being resolved can end up accessible. Unregistering one page of an idle trap also drops and reopens the whole trap, including pages outside the range. `Unmap` resets its pages before it unregisters them, so an idle trap over an unmapped user page can reopen it read-write; the AMM unmap unregisters first. Closes when: unregistering waits for the resolver and splits traps at the range
