# libSceCesCs
## change [sceCesRefersUcsProfileCp858]
- [sceCesRefersUcsProfileCp858](../../../core/libs/prx/libSceCesCs/SingleByte.hpp) (libSceCesCs) - the profile is the Cp850 one with byte 0xD5 mapped to U+20AC instead of U+0131, which is the whole high half of ICU's [ibm-858_P100-1997.ucm](https://github.com/unicode-org/icu-data/blob/main/charset/data/ucm/ibm-858_P100-1997.ucm); bytes 0x00-0x7F stay unchanged as in the other single-byte profiles, not swapped as in IBM's control mapping. A PS5 (firmware 11.60, payload process; a title process may differ) gave the same table: `sceCesSbcToUtf32` returned 0 for all 256 bytes with the CRC32 0xc831843d over the (return value, scalar) pairs, as this gives; the Cp850 profile read beside it differed in byte 0xD5 only, the 33 bytes 0x00-0x1F and 0x7F gave themselves, U+20AC converted to 0xD5 and U+0131 had no byte (`0x805C0020`; Cp850 gives 0xD5), and the UTF-8 bytes E2 82 AC gave 0xD5. ICU's table itself was not compared. On an error return the console wrote 0 to the byte output of `sceCesUtf32ToSbc` and `sceCesUcs2ToSbc` (U+0080, U+0131, U+0630, U+066A, U+FE70 and U+FFFD answered `0x805C0020`, U+D800 `0x805C0015`, U+110000 `0x805C0014`), where this leaves the output unchanged.
