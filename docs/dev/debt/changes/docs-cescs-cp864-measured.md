# libSceCesCs
## change [sceCesRefersUcsProfileCp864]
- [sceCesRefersUcsProfileCp864](../../../core/libs/prx/libSceCesCs/SingleByte.hpp) (libSceCesCs) - it follows Microsoft's [CP864.TXT](https://unicode.org/Public/MAPPINGS/VENDORS/MICSFT/PC/CP864.TXT): 0x25 is the Arabic percent sign U+066A and U+0025 has no byte, and the undefined bytes 0x9B, 0x9C, 0x9F, 0xA6, 0xA7 and 0xFF answer `UNASSIGNED_CODE`. A PS5 (firmware 11.60, payload process; a title process may differ) gave the same table: `sceCesSbcToUtf32` returned 0 for 250 of the 256 bytes with the CRC32 0xca172948 over the (return value, scalar) pairs, and it kept 0x25 as U+066A: U+0025 had no byte (`0x805C0020`) and U+066A gave 0x25. The six undefined bytes returned an error whose low 16 bits are 0x0020 (`0x805C0020` read in full for 0x9B), with 0 written as the scalar, where this leaves the output unchanged; counting that value as 0, the two CRC32 values are equal. The same difference is in the byte output of `sceCesUtf32ToSbc` and `sceCesUcs2ToSbc` and in the value output of `sceCesSbcToUcs2` on an error return; the console left the `sceCesSbcToUtf8` output unchanged for 0x9B, as this does.
