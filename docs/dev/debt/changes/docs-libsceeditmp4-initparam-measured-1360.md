# libSceEditMp4

## change [sceEditMp4InitializeParam](../../../core/libs/prx/libSceEditMp4/Export.cpp) (libSceEditMp4)

- [sceEditMp4InitializeParam](../../../core/libs/prx/libSceEditMp4/Export.cpp) (libSceEditMp4) - the size of the parameter structure and the meaning of its fields are unknown. It follows firmware 13.42's libSceEditMp4.sprx, read from its disassembly and reproduced on a PS5 Pro payload process (13.60): it returns nothing, ignores a null pointer and otherwise clears bytes 0 to 15, stores the 64-bit value 0x3f at offset 16 and the 32-bit value 700 at offset 24, and leaves the bytes from offset 28 unchanged; Firmware 13.42 checks only for null and accesses the structure directly; the 13.60 console leaves bytes from offset 28 at their sentinel values and ignores a null pointer without faulting (the fault on an inaccessible non-null pointer was not probed, it would kill the payload), so AnyPS5 skipping that write is the host-safety deviation it always was.

## change [sceEditMp4Abort, sceEditMp4Edit, sceEditMp4GetStatus, sceEditMp4Initialize, sceEditMp4SetFinishCallback, sceEditMp4Terminate and sceEditMp4Unite](../../../core/libs/prx/libSceEditMp4/Export.cpp) (libSceEditMp4)

- [sceEditMp4Abort, sceEditMp4Edit, sceEditMp4GetStatus, sceEditMp4Initialize, sceEditMp4SetFinishCallback, sceEditMp4Terminate and sceEditMp4Unite](../../../core/libs/prx/libSceEditMp4/Export.cpp) (libSceEditMp4) - answer only the checks firmware 13.42 makes before they use an open handle or Initialize goes on to allocate - checks reproduced on a PS5 Pro payload process (13.60): null arguments give `0x814B0002`, Initialize gives `0x814B0001` for the zero-first-word parameter `InitializeParam` leaves, handle untouched; an unknown handle gives `0x814B0003` writing nothing; `0x814B000F` never answered a loaded module; throw through `NotImplemented_nid_no_patch` past them; their declarations carry only the arguments those checks read, and the names are mine. No handle is open here: only a successful Initialize stores one. Each call first returns `0x814B000F` when a byte set by the module's start-up after it creates a mutex is not 1; this implementation answers as if that creation succeeded.
