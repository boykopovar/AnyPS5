- [sceKernelCallIndirectBuffer, sceKernelCallIndirectBuffer2, sceKernelCallIndirectBuffer3, sceKernelGiveDirectMemoryToMapper, sceKernelMapperGetParam, sceKernelWaitCommandBufferCompletion and the sceKernelWrite*Command AMM writers](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - firmware 4.03's libkernel.sprx, libkernel_sys.sprx and libkernel_web.sprx export all 25 NIDs but `sceKernelWriteUnmapToPrtCommand`, which no 4.03 module carries; it is kept on firmware 13.42's libkernel_sys disassembly, 13.42's libkernel unread. One file supplies both libraries rather than forwarding between providers. Final Fantasy XVI (PPSA10665) binds the NIDs to libkernel and still resolves them through kernel-family fallback (import_audit: 0 absent), so the gap is provider attribution: dlsym on libkernel and `--strict-providers` report them missing. Command helpers in [AmmExportCommands.hpp](../../../core/libs/prx/libkernel/Apr/include/AmmExportCommands.hpp)
- [sceKernelCallIndirectBuffer2](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - always writes a zero result, as `sceAmprAmmSubmitCommandBuffer2` does here; in firmware 13.42 the library passes the result pointer to a kernel ioctl, and what the kernel writes there is not known
- [AMM kernel write commands](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - signatures of the map, map direct, unmap, remap, multimap and protection writers and their GPU mask id forms taken from [ampr_emu's libkernel hook targets](https://github.com/drakmor/ampr_emu/blob/cfa85df379f6eeeb165d7badf9b648e266fe77b7/include/ampr_libkernel_hook_targets.h), which forward to the real kernel; the measure mode (`dst` null reports the size, `outSize` null skips the report) follows ampr_emu's measure-then-record calls, not confirmed on a title. Each writer builds its record with the encoder of its `libSceAmpr` command buffer sibling, so it applies the sibling's checks and writes its bytes. The GPU mask id is ignored, as by the siblings, and a protection or mask with bits above 32 is rejected, as by `sceKernelWriteModifyMtypeProtectCommand`. A wider `type` is cut to the record's 32 bits, as by that writer; the console's handling is not measured
- [AMM kernel write command checks](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - the map, map direct, unmap, remap, multimap and protection writers apply their libSceAmpr siblings' checks, not those of firmware 13.42's libkernel (compared under a CPU emulator, not measured on a console), so some arguments get a different return code. The console checks the range against the AMM virtual address ranges, accepts a size that wraps past the end of the address space, takes a different set of protection bits and, for maps and memory type changes, accepts only types 11 to 20. Where both accept a call, the recorded address, size, type and protection match
- [sceKernelWaitCommandBufferCompletion](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - signature taken from [ampr_emu's libkernel hook targets](https://github.com/drakmor/ampr_emu/blob/cfa85df379f6eeeb165d7badf9b648e266fe77b7/include/ampr_libkernel_hook_targets.h), where `sceAmprAmmWaitCommandBufferCompletion` forwards to it; like that sibling it waits for an AMM submission and returns `SCE_KERNEL_ERROR_ESRCH` for an id that was never submitted, not confirmed on a title
- [sceKernelWriteMapCommand2, sceKernelWriteUnmapToPrtCommand, sceKernelWriteWriteAddressCommand, sceKernelWriteWriteCounterCommand, sceKernelWriteWaitOnAddressCommand, sceKernelWriteWaitOnCounterCommand and sceKernelWriteEventQueueOnCompletionCommand](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - they record this project's command layout, not the console's packed commands, so the reported sizes differ and the waits' flush bit is dropped. A PRT map with a non-zero type or protection and a recorded wait on an address that is not 8-byte aligned throw: their results are unknown. The checks follow firmware 13.42's libkernel and libkernel_sys, read from disassembly and compared under a CPU emulator, not measured on a console; without the PRT flag sceKernelWriteMapCommand2 is sceKernelWriteMapCommand. As in the firmware, the PRT range check accepts an end that wraps past the top of the address space, and only size bits 14 to 40 are recorded
- [sceKernelWriteWaitOnAddressCommand and sceKernelWriteWaitOnCounterCommand](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - a negative compare passes the firmware's check (above 3 is refused) and is recorded as its low three bits, as in firmware 13.42, so -2 to -4 record modes 6 to 4. The command runner here (`_waitSatisfied` in `Apr.cpp`) implements modes 0 to 6, so a wait recorded with mode 7, for example from a compare of -1, is written successfully but throws when it runs
- [sceKernelCallIndirectBuffer, sceKernelCallIndirectBuffer2, sceKernelCallIndirectBuffer3, sceKernelGiveDirectMemoryToMapper and sceKernelMapperGetParam](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - follow firmware 13.42's libkernel_sys, read from disassembly and not measured on a console. The submit calls hand their arguments to a kernel ioctl, keeping 32 bits of the dword count, so the kernel's checks are unknown: a priority above 2, a null buffer or a dword count of 2^30 or more throws. GiveDirectMemoryToMapper requires a non-zero size and 2 MiB aligned size and alignment. sceKernelMapperGetParam copies up to 0x38 bytes of the block ioctl 0xc038ac06 fills at startup: its size, the four AMM range values, then two values nothing reads, returned as 0 until a console measurement names them. The 0x80020006 returned when its device cannot be opened is not modelled
- [sceKernelMapperGetParam](../../../core/libs/prx/libkernel/SysExports.Mapper.cpp) (libkernel and libkernel_sys) - returning `SCE_KERNEL_ERROR_EFAULT` (`0x8002000E`) for an unwritable output pointer or unreadable parameter struct is a host-safety fallback; firmware 13.42 disassembly accesses memory directly, so the console faults
