# libSceLibreSsl

## change [EVP_PKEY_id]

- [EVP_PKEY_id](../../../core/libs/prx/libSceLibreSsl/src/PkeyId.cpp) returns the key's stored type, the first 32-bit field in LibreSSL 2.5.4's `EVP_PKEY` layout. Its signature and behavior follow [p_lib.c](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/evp/p_lib.c) and [evp.h](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/evp/evp.h); PS5 behavior has not been independently measured. A null key throws `std::invalid_argument` where the reference dereferences it, as undefined input rather than a missing path.

## change [OCSP_check_validity]

- [OCSP_check_validity](../../../core/libs/prx/libSceLibreSsl/src/Ocsp.cpp) - nothing is checked on the console. It follows LibreSSL 2.5.4 [ocsp_cl.c](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/ocsp/ocsp_cl.c#L323-L392) and [a_time_tm.c](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/asn1/a_time_tm.c#L32-L209): only the 15-character `YYYYMMDDHHMMSSZ` form parses, the type field is ignored, times compare field by field, and each failed check queues one OCSP error. The current time comes from guest `time`. A null `thisupd` throws `std::invalid_argument` where LibreSSL faults. The time plus or minus `nsec` or minus `maxsec` wraps around as in that build, and a result `gmtime_s` rejects returns 0 without an error, as in the [13.42 module](https://github.com/boykopovar/AnyPS5/pull/11174#issuecomment-6406163923); its console range is unverified

## change [OCSP_resp_count and OCSP_resp_get0]

- [OCSP_resp_count and OCSP_resp_get0](../../../core/libs/prx/libSceLibreSsl/src/OcspBasicResponse.cpp) - not verified on the console. The signatures, the guest `OCSP_BASICRESP`, `OCSP_RESPDATA` and stack layouts and the results follow LibreSSL 2.5.4's [ocsp.h and ocsp_cl.c](https://github.com/libressl/openbsd/tree/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/ocsp) and [stack.h and stack.c](https://github.com/libressl/openbsd/tree/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/stack), the version in [published firmware 13.40 measurements](https://github.com/boykopovar/AnyPS5/discussions/8981#discussioncomment-19111214). Console modifications and other firmware layouts remain unverified. A null response data pointer, and a null entry array with an index in range, throw `std::invalid_argument` where that release dereferences them.

## change [OCSP_basic_add1_cert]

- [OCSP_basic_add1_cert](../../../core/libs/prx/libSceLibreSsl/src/OcspBasicResponse.cpp) is unverified on PS5. LP64 offsets (response 32 bytes, X509 references 28) follow [ocsp.h](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/ocsp/ocsp.h#L293-L298) and [x509.h](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/x509/x509.h#L268-L294); behavior follows [ocsp_srv.c](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/ocsp/ocsp_srv.c#L209-L218) and [stack.c](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/stack/stack.c#L115-L160): allocate four slots with guest realloc, append/grow, then increment X509 references. Failures return 0 with prior mutations. Null response, null cert after a successful push, and negative or signed-overflow stack counts throw `std::invalid_argument`.

## change [X509_NAME_oneline]

- [X509_NAME_oneline](../../../core/libs/prx/libSceLibreSsl/src/X509NameOneline.cpp) is unverified on PS5. It follows [LibreSSL 2.5.4](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/x509/x509_obj.c) `x509_obj.c` over the 40-byte `X509_NAME` and 24-byte `X509_NAME_ENTRY` layouts, with names from the [object table](../../../core/libs/prx/libSceLibreSsl/src/ObjectTable.cpp); without a caller buffer the text grows in a guest-heap `BUF_MEM` as `buffer.c` and `recallocarray` do, and a failed allocation reports the `BUF` and then the `X509` malloc failure. A null entry, an entry without a value, and a value without data behind a positive length throw `std::invalid_argument` where LibreSSL faults, as does a name entry stack without its array
