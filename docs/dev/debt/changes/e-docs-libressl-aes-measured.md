- [AES_set_encrypt_key, AES_set_decrypt_key, AES_encrypt, AES_decrypt, AES_ecb_encrypt, AES_cbc_encrypt, AES_cfb128_encrypt, AES_ctr128_encrypt](../../../core/libs/prx/libSceLibreSsl/src/Aes.cpp) (libSceLibreSsl) - follow LibreSSL's [aes.h](https://github.com/libressl/openbsd/blob/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/aes/aes.h) and [mode code](https://github.com/libressl/openbsd/tree/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/modes). A PS5 (firmware 11.60, payload process; a title process may differ) reproduced the FIPS-197 example vectors for 128, 192 and 256 bits (10, 12 and 14 rounds, decryption returning the plaintext), returned -2 for a 100-bit key, left the last ciphertext block in the IV after a two-block CBC call and left the keystream block in `ecount_buf` with position 0 after a 16-byte CTR call; ECB, CFB and the remaining key lengths in the mode functions are not measured. Key setup follows [LibreSSL 2.5.4's aes_core.c](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/aes/aes_core.c), the version the `X509_verify_cert_error_string` entry names: a null pointer returns -1 and a key length other than 128, 192 or 256 bits returns -2 before the key is written, and only the 44, 52 or 60 words the key length needs are written. The `AES_KEY` schedule uses that file's generic C layout (big-endian words, `rounds` 10, 12 or 14). The 2.5.4 amd64 build uses [aes-x86_64](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/aes/asm/aes-x86_64.pl) instead, which copies the key bytes without swapping, so each word is byte-reversed compared with the C layout (OpenSSL 3.0.13's x86-64 code gives the same schedules byte-reversed); the console's schedule words are byte-reversed compared with this library's (key 00 01 .. 0f: encryption `rd_key[0..3]` 03020100 07060504 0b0a0908 0f0e0d0c, decryption 7f1d1113 174a94e3 8ba707f3 c5302b4d), so a schedule the title reads or fills differs here.
