# libSceLibreSsl
## change [AES_set_encrypt_key, AES_set_decrypt_key, AES_encrypt, AES_decrypt, AES_ecb_encrypt, AES_cbc_encrypt, AES_cfb128_encrypt, AES_ctr128_encrypt]
- [AES_set_encrypt_key, AES_set_decrypt_key, AES_encrypt, AES_decrypt, AES_ecb_encrypt, AES_cbc_encrypt, AES_cfb128_encrypt, AES_ctr128_encrypt](../../../core/libs/prx/libSceLibreSsl/src/Aes.cpp) (libSceLibreSsl) - follow LibreSSL's [aes.h](https://github.com/libressl/openbsd/blob/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/aes/aes.h) and [mode code](https://github.com/libressl/openbsd/tree/bc9483725c5815efb64b6d9acc52fc5fba139212/src/lib/libcrypto/modes). A PS5 (firmware 11.60, payload process; a title process may differ) reproduced the FIPS-197 example vectors for 128, 192 and 256 bits (10, 12 and 14 rounds, decryption returning the plaintext), returned -2 for a 100-bit key, left the last ciphertext block in the IV after a two-block CBC call and left the keystream block in `ecount_buf` with position 0 after a 16-byte CTR call; ECB, CFB and the remaining key lengths in the mode functions are not measured. Key setup follows [LibreSSL 2.5.4's aes_core.c](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/aes/aes_core.c), the version the `X509_verify_cert_error_string` entry names: a null pointer returns -1 and a key length other than 128, 192 or 256 bits returns -2 before the key is written, and only the 44, 52 or 60 words the key length needs are written. The `AES_KEY` words are little-endian, as measured on the console (probe build `9409c7bfa90a`, key 00 01 .. 0f, 128, 192 and 256 bits, all 44, 52 and 60 words of both directions; encryption `rd_key[0..3]` 03020100 07060504 0b0a0908 0f0e0d0c, decryption 7f1d1113 174a94e3 8ba707f3 c5302b4d), the layout of the 2.5.4 [aes-x86_64](https://github.com/libressl/openbsd/blob/2e2c612066aa993717528a0249c15c51128d61cb/src/lib/libcrypto/aes/asm/aes-x86_64.pl) build, which copies the key bytes without swapping, not of the generic C file. libSceLibreSsl3 forwards its `AES_set_encrypt_key` and `AES_set_decrypt_key` to this library here; a second probe through the console's libSceLibreSsl3 gave the same words, and whether that module forwards or keeps its own copy is not shown. CTR leaves the last keystream block in `ecount_buf` even at a block boundary. Null pointers in the cipher and mode functions, other `rounds` values and a CFB or CTR position outside 0-15 throw.
