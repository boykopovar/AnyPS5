# libkernel

## change [sceKernelWaitEqueue](../../../core/libs/prx/libkernel/Equeue/Equeue.cpp) (libkernel) - a level-triggered user event

- [sceKernelWaitEqueue](../../../core/libs/prx/libkernel/Equeue/Equeue.cpp) (libkernel) - a level-triggered user event (`sceKernelAddUserEvent`) is reported at most once per call, as in FreeBSD `kqueue_scan` (`sys/kern/kern_event.c`), which re-queues a reported knote without `EV_CLEAR` or `EV_DISPATCH` behind the scan marker, and kevent(2), where several triggers do not produce several kevents. Not measured on a console beyond these results from a PS5 (firmware 11.60): a triggered user event stays reported; a null handle, handle 1 and a deleted equeue give `EBADF`; a count of 0 or -1, `EINVAL`. Events are reported in the order they became triggered, as FreeBSD `knote_enqueue` queues them: a user event that is triggered while idle moves behind the others, a trigger of one that is already triggered leaves it where it is, and a reported event moves to the end of the list. A payload process on a PS5 (firmware 13.590.001) with the user events 1, 2 and 3 added in that order and triggered as 2, 1, 3 reported them as 2, 1, 3 and again as 2, 1, 3 on the next wait; triggering 1 twice and then 3 and 2 changed nothing, and waits for one event each then gave 2, then 1, then 3, 2, 1 for the rest. Events of the other filters are not reordered when they fire; their order on a console was not measured. Several completions of one AMPR or VideoOut event within one call are returned as separate entries, where FreeBSD would aggregate them; the Orbis behaviour is unconfirmed
