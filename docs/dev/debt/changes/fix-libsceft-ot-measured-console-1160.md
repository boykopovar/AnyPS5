# libSceFreeType

## change [FT_Atan2]

- [FT_Atan2](../../../core/libs/prx/libSceFreeType/src/VectorPolar.cpp) (libSceFreeType) - measured in libSceFreeTypeOt.sprx on a PS5 (firmware 11.60, payload process, two identical runs; a title process may differ; prototype of two 64-bit signed arguments and a 64-bit result assumed): the axes, the diagonals and (0, 0) give what bundled [FreeType 2.15.0](https://github.com/freetype/freetype/blob/37515cf56ba3349656049edbed89ffc6f6466f2d/src/base/fttrigon.c) gives, except dx < 0 with dy = 0, which returns +180 degrees (0xb40000) where FreeType returns -180 degrees; the adapter returns +180 degrees there. The console computes inputs from 2^31 up in 64 bits (dx = 0x80000000 gives 0; dy = 0x7fffffffffffffff gives 90 degrees); a guest value outside the host `FT_Fixed` range still throws on Windows, where the native type is 32 bits (not matched in this change)

## change [FT_Vector_Transform, FT_Matrix_Multiply and FT_Matrix_Invert]

- [FT_Vector_Transform, FT_Matrix_Multiply and FT_Matrix_Invert](../../../core/libs/prx/libSceFreeType/src/Geometry.cpp) - measured in libSceFreeTypeOt.sprx on a PS5 (firmware 11.60, payload process, two identical runs; a title process may differ; prototypes and 8-byte coordinates assumed): in-range results, equal those of the adapter; the console computes inputs outside signed 32 bits in 64 bits (not matched in this change). Names and NIDs follow the [PS5 3.20 inventory](https://github.com/DNNDHH/PS5-3.20_Libs/blob/b2a77c09cd71c01f34c790cfbe98c751a13262ad/libSceFreeTypeOt.c). Geometry follows bundled [FreeType 2.13.3](https://github.com/freetype/freetype/blob/42608f77f20749dd6ddc9e0536788eaad70ea4b5/src/base/ftcalc.c) built for x86-64 LP64, including on Windows: multiplication narrows operands and individual products to signed 32 bits, then adds or subtracts in 64 bits; inversion uses unsigned 64-bit wrapping division intermediates. Bundled FreeType 2.15.0 differs for wider inputs.

## change [FT_Outline_Check, FT_Outline_Get_CBox]

- [FT_Outline_Check, FT_Outline_Get_CBox](../../../core/libs/prx/libSceFreeType/src/Outline.cpp) (libSceFreeType) - measured in libSceFreeTypeOt.sprx on a PS5 (firmware 11.60, payload process, two identical runs; a title process may differ; prototypes and the 40-byte outline layout assumed): a valid outline, an empty one and a tag value of 7 return 0; a contour end beyond n_points and ends that do not increase return 6 on the console, 20 here, as bundled [FreeType 2.15.0](https://github.com/freetype/freetype/blob/37515cf56ba3349656049edbed89ffc6f6466f2d/src/base/ftoutln.c) returns its invalid-outline code (not matched in this change). The control box of 6 points, of 0 points (all zero, written) and of coordinates above 32 bits (full 64 bits) equals the adapter's, including its unsigned 16-bit counts and contour endpoints. Contour checking does not validate point tags

## change [FT_Outline_Reverse, FT_Outline_Translate]

- [FT_Outline_Reverse, FT_Outline_Translate](../../../core/libs/prx/libSceFreeType/src/Outline.cpp) (libSceFreeType) - measured in libSceFreeTypeOt.sprx on a PS5 (firmware 11.60, payload process, two identical runs; a title process may differ; prototypes and the 40-byte outline layout assumed): translation is 64-bit modular addition (2^63-1 plus 1 gives 0x8000000000000000), as here; reversal toggles the reverse-fill flag and reverses all points of each contour, the first one too, where the adapter keeps the first point as bundled [FreeType 2.15.0](https://github.com/freetype/freetype/blob/37515cf56ba3349656049edbed89ffc6f6466f2d/src/base/ftoutln.c) does (not matched in this change); the tag order was measured with equal tags only. Coordinates outside the host `FT_Pos` range still throw if the modified outline is later rendered on Windows
