# libSceHttp2

## remove [libSceHttp2 offline requests]

## change [libSceHttp2 asynchronous requests]

- [libSceHttp2 asynchronous requests](../../../core/libs/prx/libSceHttp2/Export.cpp) - `sceHttp2SendRequestAsync` copies the body and queues a completion whose `result` is the transport result; `sceHttp2ReadDataAsync` reports the bytes read. With `APS5_NET_DISCONNECTED` set, the send starts no worker, queues `0x80431063` and triggers the user event itself; `sceHttp2WaitAsync` returns it from the request's queue. This unblocks offline mode in PPSA24263 (#11591). `0x80431063` is the network error the synchronous send returns and libSceHttp's network error ([HttpErrors.hpp](../../../core/libs/prx/libSceHttp/src/HttpErrors.hpp)); libSceHttp2 also returns libSceHttp-range codes such as `0x804311FE`, but the code a console returns for an offline libSceHttp2 send is not measured. The worker triggers the kqueue user event (equeue 0, event id 8, user data 16, layout inferred from PPSA17221); a null `kqueue_option` only queues the completion. The trailing `option` is ignored although 11.00 rejects a non-null one with `0x817b11fe` because PPSA22408 passes one. A failed user-event trigger is carried to the waiter as a completion failure, so `sceHttp2WaitAsync` throws it. A second submission while one is queued is rejected by 11.00 with `0x817b1021` and queued here instead. The read buffer must stay valid until its event or its completion, a worker keeps the transport alive until it observes cancellation, and a transport exception is rethrown from the wait. These calls follow the firmware 11.00 module; the `libSceHttp2` module bundled with PPSA20397 differs: its `sceHttp2ReadDataAsync` (`bGN-6zbo7ms`, 0x2b40) is a 10-byte stub that always returns `0x80436063`, and its `sceHttp2WaitAsync` (0x2e90) never reads `timeout`. Whether PPSA20397 still behaves correctly when its asynchronous read completes with data instead of returning `0x80436063` is not measured.

## change [sceHttp2WaitAsync]

- [sceHttp2WaitAsync](../../../core/libs/prx/libSceHttp2/Export.cpp) - result validation and copy-out still access guest pointers directly, so an unmapped result pointer can fault the host.

## add Functional

- [sceHttp2WaitAsync](../../../core/libs/prx/libSceHttp2/Export.cpp) - with nothing queued or pending (drained or never sent) it returns `0x817b1065` at once, whatever the timeout (0 and 200000 measured; null follows them, unmeasured), leaving both outputs untouched. A completion already queued is consumed without changing `*timeout`. With an asynchronous operation still in flight, a null `timeout` blocks, `*timeout == 0` polls and returns `0x817b1079` at once, and a nonzero `*timeout` is a microsecond deadline that returns `0x817b1079` on expiry (`0x8002003c` remapped at `0x9a79`) and receives the remaining microseconds. A payload on firmware 13.590.001 measured the idle, pending and queued results ([#17735](https://github.com/boykopovar/AnyPS5/pull/17735)). A null `result` is `0x817b1225`; a non-null trailing argument or non-zero `reserved` is `0x817b11fe` (`0x1d21`, `0x1cca`, `0x1cd3`). `event_type` is 0 for send and 1 for read, from the `+0x1600` completion kinds.

- [libSceHttp2 asynchronous completion](../../../core/libs/prx/libSceHttp2/Export.cpp) (libSceHttp2) - the overall deadline set by `sceHttp2SetTimeOut` does not apply to a request whose transport `sceHttp2SendRequestAsync` created: with a 1 s overall timeout and a server that never answers, a payload on firmware 13.590.001 queued no completion and `sceHttp2WaitAsync` returned `0x817b1079` only when its own timeout expired, while `sceHttp2AbortRequest` completed it with `0x817b1080`. Connect, send and receive timeouts still bound the operation, and the later asynchronous reads ignore the overall deadline too; a synchronous send followed by an asynchronous read keeps it, unmeasured. Deleting a request while a wait is blocked measured as 0 with an `0x817b1080` completion of the operation's own kind and about 3 s of a 4 s timeout left: `sceHttp2DeleteRequest` now queues one per operation in flight, after stopping the transport, so the read buffer is not written when it returns. Unmeasured: the console's kqueue user event there (none here), an unwatched completion (dropped here) and a synchronous call interrupted by deletion (still throws here); a wait starting after the erase returns `0x817b1100`.
