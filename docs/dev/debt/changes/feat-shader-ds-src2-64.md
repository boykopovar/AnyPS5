# shader

## change [DS src2 operations]

- [DS src2 operations](../../../core/shader/recompiler/Translation/src/MemoryInstructions/SharedMemoryInstructions.cpp) (`ds_*_src2_*`) read `DS[B]`, with `B = A + 4 * sext(offset1[6:0]:offset0)`, and then update `DS[A]` with the matching atomic, so the read of `B` is not atomic with the update of `A`. The 64-bit forms follow the same offset rule and update `DS[A]` with the matching 64-bit atomic: an RX Vega 56 (gfx900, GCN5, ROCm HSA, wave64) run measured the qword source at `A + 4 * offset` rather than `A + 8 * offset`, the result at `A`, the source left unchanged, a carry out of the low dword, signed `ds_min_src2_i64`, unsigned `ds_min_src2_u64`, `ds_max_src2_f64`, `ds_xor_src2_b64` and `ds_write_src2_b64`. gfx1013 and RDNA2 remain unmeasured: LLVM 18 rejects the SRC2 mnemonics for gfx103x, and a hand-encoded 64-bit SRC2 timed out on gfx1036 in the same run. A second offset of 1, which puts the 64-bit source at four-byte alignment, aborted that kernel on gfx900 under ROCm; whether that is an alignment fault or a problem in the runner is not established, and the translator computes the unaligned load instead of refusing it. The form that takes the offset from the address (`offset1[7]` set) and GDS still throw: whether the LDS address keeps `A[31:17]` in that form is not documented. `ds_min_src2_f32`, `ds_max_src2_f32` and `ds_add_src2_f32` follow the LDS float atomics rule above, inferred from `ds_min_f32`, `ds_max_f32` and `ds_add_f32` measured on RDNA2 (gfx1035), which has no src2 opcodes; the f32 src2 forms were not measured on GFX10.1.
