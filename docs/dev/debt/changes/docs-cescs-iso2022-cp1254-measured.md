# libSceCesCs
## change [ISO-2022-JP profiles and string conversions]
- [ISO-2022-JP profiles and string conversions](../../../core/libs/prx/libSceCesCs/Export.cpp) (libSceCesCs) - the signatures follow the MBCS string family by analogy (none in the type database). The UTF-16 and UCS-2 forms share the converters; the UTF-16 form was measured together with the UTF-32, UTF-8 and length forms. `sceCesIso2022UcsContextInit` with a null profile zeroes 256 context bytes and answers `INVALID_PARAMETER`, from a PC run of the firmware 13.42 module; a PS5 (firmware 11.60, payload process; a title process may differ) did the same (`0x805C0001`, all 256 bytes of a `0xAA` context zeroed) and answered a null context `0x805C0001`. Measured on a PS5 through the UTF-32 and UTF-8 forms (every BMP scalar, every designation then every byte and 94x94 pair, 46 strings per profile): RFC 1468 starts in JIS X 0201 Roman (`ESC ( B` and `ESC ( J` both select it) and uses the strict JIS X 0208 table; the code pages start in ASCII and use CP932's table plus the JIS forms. No profile has JIS X 0212. A trailing designation is not counted; one at the buffer end answers `SRC_BUFFER_END`. The encoder returns to the initial set only if it left it. The same console agreed in 10 of 12 probes per profile for RFC 1468, CP50221 and CP50222 (`ABC`, `ESC $ B`, `ESC $ @`, `ESC ( J`, a JIS X 0208 pair, `SO 41 SI`, a cut and a trailing designation, a pair without a closing designation) and differed in two, which this now reproduces for the inputs measured: `ESC & @` before a designation was skipped (the pair then decoded to U+3042 with `0x805C0011` and 8 bytes used) and a lone `ESC x` answered `0x805C0011` with 0 used; other `ESC &` finals and other two-byte escapes were not measured; CP50222 decoded `SO 41 SI` to U+FF81 with `0x805C0011` and 2 used, where RFC 1468 and CP50221 answer `0x805C0015`.
## change [Cp1254 and Cp1258 unassigned bytes, and surrogates in sceCesUtf32ToSbc]
- [Cp1254 and Cp1258 unassigned bytes, and surrogates in sceCesUtf32ToSbc](../../../core/libs/prx/libSceCesCs/SingleByte.hpp) (libSceCesCs) - bytes `81 8D 8E 8F 90 9D 9E` of 1254 and `81 8A 8D 8E 8F 90 9A 9D 9E` of 1258 answer `0x805C0020` both ways, as [rooklz](https://github.com/boykopovar/AnyPS5/pull/10183#issuecomment-6389941634) measured on a PS5 through `sceCesSbcToUtf32` and `sceCesUtf32ToSbc`; BunnyFl's [13.42 run](https://github.com/boykopovar/AnyPS5/pull/9912#issuecomment-6403897082) gives the same bytes. On a PS5 (firmware 11.60, payload process; a title process may differ) the MBCS context conversions (`sceCesMbcsStrToUtf16Str` and `sceCesMbcsStrGetUtf16Len`, 11 cases for Cp1254 and 13 for Cp1258) gave the same: the listed bytes answered `0x805C0020` with nothing used, bytes `0x80`, `0x82` and `0x9F` converted to U+20AC, U+201A and U+0178, and `A`, `0x81`, `B` stopped after `A` with `0x805C0020`. The same sweep found `sceCesUtf32ToSbc` answering `0x805C0015` (`ILLEGAL_CODE`) for a surrogate with every single-byte profile, as it does here; the other UTF-32 forms were not measured. That console answered `0x805C0015` for `sceCesUcs2ToSbc` of U+D800 and for `sceCesUtf16ToSbc` of a lone low surrogate with Cp1252, Cp1254, Cp1258, ISO 8859-1 and ISO 8859-15, where those keep `INVALID_ENCODE` here.
