# libSceXml

## add Functional

- [Document::serialize](../../../core/libs/prx/libSceXml/src/Serializer.hpp) (libSceXml) - follows `libSceXml.sprx` of firmware 13.40 (sha256 `810de3883c4d988a5b2fd6306dfb0a5fee02b987682922540cd11a8c242c88d6`, `0x41c0` and the walk at `0x15fa0`), run natively on an x86-64 host with its imports replaced by host functions, not measured on a console. Of 480,000 serializations (30,000 generated documents, the eight builder settings and both declaration flags), the 117,132 that write nothing without the declaration throw as described below, and of the other 362,868 all are identical but 228, every one with `setResolveEntity(true)`, where this library's parser already reads the document differently from the module. The first point below lists module behaviour this keeps on purpose; the rest is not modelled:
  - Kept on purpose: the root element and its following siblings are walked; an empty element's name is written again as a closing tag after the next sibling that is not an element (`<a/>t</a>`); a comment is written as `<!--` and its text without `-->`; CDATA, processing instructions and every other node type are written as their skipped text; a reference does not close an open start tag; a null attribute name, attribute value or entity name is written as `(null)`, as the console's `snprintf` and this library's own write it.
  - With no declaration and nothing written, the module returns its new output buffer unterminated, so the result is whatever that memory held; that throws, as does a null element name, which the module passes to `strlen`.
  - The module builds the text in blocks from the title's allocator (growing by doubling below 0x801 bytes and by 0x200 above) and copies it into the document's block; here it is host memory, so a title that counts allocations or runs out of memory sees a difference, and the module's out-of-memory result `0x80850001` is never returned.
  - The result stays valid until the next `serialize` of the same `Document` or its destruction; how long the module's pointer stays valid after a later call is not measured.
  - Generated documents the parser here reads differently from the module, which the result shows: with `setResolveEntity(true)`, `<list id='e" b="&foo;" x:y="&foo;'/>` gives the attribute value `e" b="&foo;" x:y="&f` in the module and the whole value here, and in some documents that stop with `0x8085000a` the module reads a null value for an unterminated attribute that holds an unresolved reference.
  - Writable documents walk `WritableTree` through the same serializer; serializing mutated writable documents was not run separately against the 13.40 module.
