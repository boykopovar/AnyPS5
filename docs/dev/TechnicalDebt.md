# Project technical debt

Entries about one library or component are in [debt](debt/), one file per library or component, under the same sections as this page. Entries that belong to none stay here. An entry may end with `Closes when:` and the measurement, title or test that would close it, such as `Closes when: measured on a PS5`, so the entries a contributor can re-check are found by searching for it. It may also end with `Labels:` and labels that replace what [`tools/debt_report.py`](../../tools/debt_report.py) infers for that family: `console`, `firmware`, `gpu`, `title` or `code` for what would close it, `no-test` or `tested`, and `windows`, `macos` or `linux`.

### Build

- The full Windows build requires x86-64 MinGW-w64 GCC with POSIX threads and DWARF or SEH exception support for System V ABI functions. The build checks these capabilities; see the [Windows build requirements](BUILD.md#windows-setup-and-troubleshooting) for the validated WinLibs and MSYS2 toolchains.
- Even compiled prx libraries on Windows require nearby (static linking of these dependencies causes conflicts):
  - libgcc_s_seh-1.dll
  - libstdc++-6.dll
  - libwinpthread-1.dll

### Silent stubs

Throughout the project, every function at every stage either **does exactly what it's supposed to or throws an exception**. The exceptions are listed under **Silent stubs** in each library's file in [debt](debt/).

### Functional

- Controller haptic PCM that no controller sound card plays (a DualSense over Bluetooth, or any other controller) drives motor rumble from its per-channel RMS (large/small motor, scale 2x, below 0.01 ignored, 80 ms hold); the mapping approximates waveform energy and is not measured against console hardware
- [Cancellation coverage](ARCHITECTURE.md#thread-cancellation) checks deferred request handling and recovery, not full asynchronous support or console ABI compatibility. Cancellation during file/socket I/O, sleep interruption, cancellation versus exit/detach, condition signal conservation under cancellation, and safe rejection of non-null invalid or reclaimed thread handles remain unverified. No console title or homebrew establishes the cleanup NIDs or buffer layout. Accepted asynchronous mode currently has no diagnostic for its deferred behavior.
- `--to-intel` guest module trampolines are covered only by a synthetic relinker test; no game title has been verified with them on Linux or Windows.
- [Quick syntax checks](../../tools/check_compile.py) do not support Windows-style response-file quoting. GNU response files reject empty options, byte order marks, quoted CRLF, Windows text-mode EOF markers and escapes whose meanings differ between GCC and Clang, including backslashes in single quotes, most backslashes in double quotes and escaped line endings. Supply expanded compile arguments for those forms; the Ninja fallback uses `ninja -t compdb -x`.
- [Quick syntax checks](../../tools/check_compile.py) do not model every compiler option's operand count. A preprocessing mode following an unrecognized option without a joined value is rejected rather than risk removing that option's operand. Compiler wrappers with their own option grammar are not covered, except a leading `cmake -E env`, whose options other than `NAME=VALUE`, `--unset=`, `--modify` and `--` are rejected. Forwarded frontend actions (`-Xclang`, `-Xpreprocessor` and their joined forms) are rejected. Comma-forwarded options (`-Wp,`) allow only recognized macro/include operands; response-file tokens are rejected even as operands, and other options are rejected because unmodeled actions or output operands could bypass syntax analysis or write outputs. See the [Clang option grammar](https://clang.llvm.org/docs/ClangCommandLineReference.html).
- [Quick syntax checks](../../tools/check_compile.py) reject `-save-temps=` and `--save-temps=` values other than `cwd` and `obj` instead of passing them to the compiler: an unknown value fails on GCC, while newer Clang builds take any value as an output prefix and write preprocessed files even under `-fsyntax-only` (measured on Apple clang 21), so a passed-through mode either fails the check on one compiler or silently writes outputs on the other.

### ps5lift

#### Bugs

Each of these gives a wrong result, corrupts state or reports a misleading error instead of stopping cleanly, and most have no fixture that would catch them.

- A divide error (a zero divisor or a quotient wider than the operand) stops the program with its address, as `ud2` and `int3` do; a guest exception handler does not see it.

- Unnormals, pseudo-NaNs and pseudo-infinities are computed as SoftFloat normalises them, instead of raising IE and returning the indefinite; `fxam` already classifies them as unsupported.
- [`PS5LIFT_MXCSR_MASK`](../../ps5lift/runtime/include/ps5lift/State.h) is 0xffff where Zen 2's MXCSR mask is 0x2ffff: the PS5's `cpuid` reports misaligned SSE, which allows MXCSR bit 17, and `ldmxcsr` and `fxrstor` with bit 17 set stop the program instead of taking the value.

- [Discovery](../../ps5lift/lifter/src/Discovery.cpp) decides whether an address a RIP-relative `lea` takes is a function by how the code after it uses it. That lets data through: a string or table in an executable segment whose address is passed to a call, stored or spilled is decoded as code, which stops the lift or adds bogus call targets. A target inside a known function splits it, which can cut a guarded jump table off from its jump. An error in a start found this way does not name the `lea`. Checking the target itself (that it lies between known functions and decodes cleanly to a terminator) would replace the use patterns.
- `TableBound` accepts a `cmp`/`ja` guard reached through its taken edge, where the index is above the bound; walks past calls that clobber a caller-saved index, which `ReachingDefinitions` does not; and takes `sub idx, K; ja` as a bound on the result, which wraps. Each gives a table that is marked guarded but too short, whose missing cases stop in `ps5lift_dispatch`. A guarded table whose entries run past readable data is also cut short there without an error.
- The linear sweep keeps only data references outside executable segments, so a reference into a table that shares a segment with code does not end the table before it.
- `CalledImport` recognises a PLT stub only when its first instruction is the `jmp`, so a call to `setjmp` through an IBT stub (`endbr64; bnd jmp`) gets no resume point; the fixtures build with `-fcf-protection=none`. Its stub probe decodes outside `DecodeReached`, so an undecodable call target fails without naming the call.
- [GuestImage](../../ps5lift/lifter/src/GuestImage.cpp)'s filter for the CIE personality drops LSDA landing pads outside their FDE, such as those a compiler moves into a cold section, which then are not resume points.
- `repne movs` and `repne stos` run once; the F2 prefix should repeat them as `rep` does.
- A 32-bit `bsf` or `bsr` with a zero source, and a 32-bit `cmpxchg` whose comparison fails, clear the upper half of the destination register, which x86 leaves untouched.
- A locked read-modify-write (`cmpxchg`, `cmpxchg8b`, `xadd`, `xchg`) whose memory operand crosses a page boundary raises SIGBUS on aarch64, where x86 completes it or raises a page fault.
- A taken 16-bit near branch (66-prefixed) goes to the 64-bit target instead of `(next + rel16) & 0xffff`.
- Some EVEX (AVX-512) forms produce IR that does not verify ("Operand is null") instead of being reported as unsupported.

#### Gaps

- [Discovery](../../ps5lift/lifter/src/Discovery.cpp) seeds functions from the entry point, `DT_INIT`, the function exports, the `.symtab` function symbols, `.eh_frame`, relocation targets in executable segments and the addresses code takes with a RIP-relative `lea` (see the bugs above), then follows direct calls. It reads the init and fini arrays only through their relocations. A function only reached through a pointer that none of these finds stops at run time in `ps5lift_dispatch`.
- [Jump tables](../../ps5lift/lifter/src/Discovery.cpp) whose guard is not recognised, such as one that compares a stack slot and loads the index from another, are sized by the data references around them. A reference into the table ends it early, which stops at run time in `ps5lift_dispatch` when a missing case runs; data that nothing refers to after the table, with words that happen to point into the function, adds entries, and one that lands inside an instruction stops the lift.
- [GuestImage](../../ps5lift/lifter/src/GuestImage.cpp) applies `R_X86_64_64`, `GLOB_DAT`, `JUMP_SLOT` and `RELATIVE` at lift time, at the executable's link addresses and at the base `ps5lift` gives each module; `R_X86_64_DTPMOD64`, `DTPOFF64` and `TPOFF64` against the image's own symbols, and packed relative relocations (`DT_RELR`); any other relocation type, including copy relocations and TLS relocations against another image's symbols, stops the lift, as do a relocation against an IFUNC and a dynamic table without its size tag. IFUNC resolvers are not run. An unresolved weak undefined symbol becomes an import like any other, so a guest whose weak reference no AnyPS5 library bridges fails to link rather than reading 0. An image's references to its own symbols are not interposed by an earlier image's, as `ld.so` would interpose them without `DT_SYMBOLIC`. PS5 inputs have to be relinked first; `ps5lift` does not read SELF or SCE dynamic tables itself.
- A `call` or `jmp` through an import slot is lifted as a direct call to the import, which is wrong if guest code rewrites that slot.
- A lifted program loads only the guest modules it was lifted with, those its executable needs through `$ORIGIN`.
- [The runtime](../../ps5lift/runtime/src/Runtime.cpp) maps the whole image read-write (through AnyPS5's guest arena when its libc is linked in), and runs modules' initializers but not the executable's nor any finalizer; the relinker's entry stub is the only entry contract tested.
- [The lifter](../../ps5lift/lifter/src/instructions/Dispatch.cpp) reports these as unsupported, and reaching one at run time stops the program: gathers, `maskmovdqu` and `maskmovq`, `rcl` and `rcr`, `pushf` and `popf`, `xlat`, `enter`, `psign`, `mpsadbw`, `movnti`, `movntpd`, `movq2dq`, `movdq2q`, the conversions between MMX and SSE registers (`cvtpi2ps`, `cvtps2pi` and the rest), `vzeroall`, `xsave`, `xsavec`, `xsaveopt` and `xrstor` with their 64-bit forms (the runtime's `cpuid` reports XSAVE, XSAVEOPT and XSAVEC, so code that checks it can reach them), the x87 instructions listed below, `syscall`, `bt`, `bts`, `btr` and `btc` with a register bit offset and a 32-bit address, far `call`, `jmp` and `ret`, a 16-bit `leave`, `fnstenv` and `fldenv` with the 14-byte 16-bit environment, `shld` and `shrd` with 16-bit operands, whose counts above 16 give undefined results, and 16-bit `bswap`, which is undefined.
- SSE4a's `extrq` and `insertq` are unsupported with the field in a register or past bit 63. Their immediate forms keep the destination's upper quadword, which AMD leaves undefined, and were checked against the APM's definition only, since no AMD machine is at hand.
- AES-NI and `pclmulqdq` lift on 128-bit registers only: VAES and VPCLMULQDQ on 256-bit registers are AVX-512-era extensions the reported Zen 2 lacks, and code that checks `cpuid` does not reach them.
- [`cpuid` and `xgetbv`](../../ps5lift/runtime/src/Cpuid.cpp) answer as an AMD Zen 2: with the signature of AMD's 4700S desktop kit, which is built on the PS5's chip (family 17h, model 47h, stepping 0), and with the user-mode extensions LLVM enables for `znver2` plus the optional ones AnyPS5's host check lists for the console. None of it is measured on a console. The highest leaves reported are 0xd and 0x80000001, so code reads the cache, topology and brand-string leaves as absent; leaves 5 and 6 and `xgetbv` of a register other than XCR0 stop the program.
- A function's frame counts as private, and its accesses through `rsp` and its frame pointer as plain, when no instruction of that function hands out an address in it ([FunctionLifter.cpp](../../ps5lift/lifter/src/FunctionLifter.cpp), `HandsOutFrameAddress`). Code that runs on another function's frame but is lifted as a function of its own, such as a cold part a compiler split off, decides for itself, so it can read a local its parent handed out without ordering.
- Loads from an image's segments without `PF_W` are plain ([FunctionLifter.cpp](../../ps5lift/lifter/src/FunctionLifter.cpp), `InReadOnlySegment`). The runtime stops a guest that makes such a segment writable, but nothing stops one that maps those pages a second time, writable, at another address.
- A direct call stores only the registers its callee names ([Discovery.cpp](../../ps5lift/lifter/src/Discovery.cpp), `CloseEffects`), so a handler that `sceKernelRaiseException` delivers in the middle of a function can find registers in the state that are older than the last call.
- An unaligned ordered load or store is a plain access with a fence. x86 makes an unaligned access within a cache line single-copy atomic; aarch64 makes a plain one atomic only within 16 bytes with FEAT_LSE2, and not at all without it. Locked instructions, `xchg`, `xadd` and `cmpxchg` still declare their natural alignment, so an unaligned one, a split lock on x86, faults. Vector loads and stores wider than 64 bits are not ordered.
- Lifted calls nest on the host stack, which the runtime sizes at 512 MiB for every guest thread, those libkernel starts included; a native thread that calls guest code has the host stack its creator gave it.
- `longjmp` unwinds lifted frames ([Jump.cpp](../../ps5lift/runtime/src/Jump.cpp)) but not native frames between them, so a `longjmp` out of a guest callback that native code called stops the program. Its target frame is the innermost one with a `setjmp` call whose entry stack pointer is at or above the saved one, which assumes the frame did not move its stack pointer above that value after `setjmp`.
- A `ret` on a switched stack resumes only in a frame on the current host stack, at one of its resume points, so a guest context switch to another stack (a coroutine) stops the program, and one that leaves by an indirect `jmp` rather than a `ret` is not followed. A helper that assigns RSP and returns on a shifted stack, rather than adjusting it with `add` or `sub`, would be read as a switch.
- The status flags are not kept in the state: only DF crosses calls, returns and dispatch, or all of them with `--preserve-flags`. `pushf` and `popf` are not lifted.
- Under qemu 8.2.2 the lifted vector fixture built for `neoverse-v2` at -O0 (relaxed) and -O3 (TSO) crashes with SIGSEGV on a store to mapped, writable memory, and the same binary prints the expected output with `-one-insn-per-tb`; builds for `neoverse-n1` and every x86-64 build pass. The same `neoverse-v2` builds, SVE included, pass natively on the GB10 (`ps5lift.py fixture --cpu neoverse-v2`), so this is a qemu translation bug. The test driver runs aarch64 code under qemu with `-one-insn-per-tb` to avoid it.
- [FMA](../../ps5lift/lifter/src/instructions/Float.cpp) NaN priority (left multiplicand, right multiplicand, addend) was measured on an Intel Xeon; Zen 2 is unverified.
- Which NaN `dpps` and `dppd` return when two or more products are NaN or infinite differs between x86 implementations: an Intel Goldmont Plus and a Coffee Lake add the products in different orders, neither the SDM's, and Zen 2 is unmeasured. The lifter follows the SDM's pseudocode, and the `sse41` fixture hashes such a result as one canonical NaN.
- `rcpps`, `rcpss`, `rsqrtps` and `rsqrtss` return the correctly rounded `1/x` and `1/sqrt(x)`, not Zen 2's approximations.
- `stmxcsr` reports the exception flags the host FPU raised; an operation that `--float exact` computes with integer code, such as `vcvtps2ph` with an immediate rounding mode, raises none.
- On aarch64 DAZ and FTZ both set `FPCR.FZ`, which flushes inputs and outputs and judges a result tiny before rounding: a guest with only one of the bits flushes both ways, and FTZ flushes a result that x86 rounds up to the smallest normal. `FPCR.AH` would match x86 but stays clear ([floating point](PS5LIFT_DESIGN.md#floating-point)). The console's MXCSR sets both bits, and the fixtures only exercise both together.
- LLVM assumes the default floating-point environment, so an operation it constant-folds uses round-to-nearest whatever the guest MXCSR says.
- Data imports are told apart from function imports by the symbol's ELF type; an untyped undefined symbol is treated as a function. Copy relocations and TLS imports are not supported.
- Native calls through a guest function pointer read from memory pass only the arguments and results the host keeps in registers, cost a signal each, and the x86-64 host's trampoline has not run. [Callbacks](../../ps5lift/runtime/include/ps5lift/Bridge.hpp) take and return scalars only, and each signature has 256 thunks; the 257th distinct guest address for one signature stops the program. The guest state a foreign native thread gets on its first callback lives until that thread exits.
- An SSE exception that MXCSR unmasks raises no SIGFPE, where the console raises one: [`ps5lift_apply_mxcsr`](../../ps5lift/runtime/src/Runtime.cpp) gives the host FPU MXCSR's rounding mode, DAZ and FTZ but never its exception masks, for lifted code's `ldmxcsr` and a lifted libc's `feenableexcept` alike.
- A binary128 `long double` from host code reaches the guest through `GuestCpuStoreExtended` and the bridges' `ReturnExtended` rounded once more, to the x87 format's 64-bit significand in the control word's rounding mode ([X87.cpp](../../ps5lift/runtime/src/X87.cpp), `ps5lift_extended_from_host`), so a result that host math already rounded to binary128 is rounded twice, which can be off by one in the last place, and the precision control is ignored: a guest that sets it to 24 or 53 bits still gets 64.
- [GuestCpu](../../ps5lift/runtime/src/GuestCpu.cpp), the guest FPU state that a lifted AnyPS5 libc reads: x87 is only its control and status words, so `fegetenv` reports every x87 register empty; `fwait` with an unmasked pending x87 exception ends the program where the console raises SIGFPE; the MXCSR support mask is reported as `0xffff`, not measured on a PS5. Flags that lifted arithmetic raises reach `fetestexcept` through the host FPU, but LLVM may reorder or fold floating-point operations around a call because it assumes the default environment.
- [x87](../../ps5lift/runtime/src/X87.cpp): the transcendental instructions (`fsin`, `fcos`, `fsincos`, `fptan`, `fpatan`, `f2xm1`, `fyl2x`, `fyl2xp1`), `fxtract`, `fbld`, `fbstp`, `fsave`, `frstor`, `fnop` and `ffreep` are reported as unsupported. `fprem` always finishes the reduction in one step, so C2 is never set, and the C bits of an `fprem` with a NaN result and the rest of the x87 behaviour were measured on an Intel Xeon, not on Zen 2. An unmasked x87 exception ends the program at the next `fwait`, not at the next x87 instruction, and `fnstenv`, `fxsave` and `fxsave64` record zero instruction and operand pointers and last opcode. `fxsave` writes the first 416 bytes of its area and leaves the reserved rest alone; the `fx-state` fixture matched an Intel Pentium Silver (Goldmont Plus) for the words, MXCSR and its mask, the loaded registers and an XMM register.

#### Tests

- Every fixture is built for `znver2`, so the compiler encodes SSE with VEX, and the only legacy SSE forms tested are AES, `pclmulqdq`, SHA, MMX and a set of scalar arithmetic, comparison, rounding and conversion forms, which come from assembly. `vector.c` and `float.c` use AVX throughout, so covering the packed legacy forms needs SSE-only builds of their tests.
- No test runs `--float fast`, `--preserve-flags` or `--emit-ir`, and no fixture splits an image into more than one part, so calls between the parts of one image are tested only by EVO Player.
- Untested paths: division traps, jump tables sized by layout, and the runtime's reports of a guest `int`, a full callback pool, a `longjmp` through native code, a resume a frame has no point for and a jump that leaves a closed jump table.
- The TSO check in `threads.c` can only fail when the lifted code runs on aarch64 hardware.
