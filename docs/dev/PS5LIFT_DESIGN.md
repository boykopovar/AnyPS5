# Design

## Goal

Run PS5 titles natively on aarch64 Linux (first target: DGX Spark, GB10 with Cortex-X925/A725 and a Blackwell GPU) by recompiling the guest's x86-64 code ahead of time. AnyPS5 already reimplements the system libraries, AGC and the shader recompiler as C++. Those build natively for aarch64, so after recompilation nothing in the process is x86-64.

PS5 titles suit static recompilation: retail games cannot generate code at run time, every executable and module ships with the title, executables carry relocations and `.eh_frame`, and imports are named by NID.

## Pipeline

```
eboot.bin + sce_module/*.prx
  -> unwrap_self.py  AnyPS5's tool: each decrypted SELF container to a plain ELF
  -> AnyPS5 relinker SCE dynamic tables and modules converted to a Linux x86-64 ELF whose imports are named by NID
  -> GuestImage      AnyPS5 ElfReader: segments, PT_TLS, the dynamic segment's symbols and relocations, applied statically; eh_frame function starts
  -> Discovery       Zydis recursive descent from every known start; call targets become new starts until a fixpoint; jump tables
  -> Lifter          one LLVM function per guest function, void guest_<address>(Ps5LiftState*), in parts of about 50000 instructions
  -> Codegen         each part on a thread of its own: LLVM O2, then an object for the target triple and CPU; one archive of all parts
  -> link            with the runtime, the import bridges and the native AnyPS5 libraries
```

## Images

A program can be several ELF images: the executable and the modules it names in `DT_NEEDED` as `$ORIGIN/<path>`, which is how the AnyPS5 relinker names the `.guest.prx` modules it converts from a title's `sce_module` directory. Any other `DT_NEEDED` entry is a native library, reached through bridges. `GuestProgram::Load` ([Program.cpp](../../ps5lift/lifter/src/Program.cpp)) reads the executable at its link addresses and the modules breadth-first, each position-independent module at the next 16 MiB boundary after the previous image and its import addresses, and relocates them only once all are read: an undefined symbol binds to the first image in that order that exports it, as `ld.so` would bind it, and only a symbol no image exports becomes an import. A relocation against a symbol the image defines binds to its own definition.

Discovery runs per image, from its entry point, `DT_INIT`, its exported functions, relocation targets, symbols, `.eh_frame`, and the addresses code takes with a RIP-relative `lea` and then stores, pushes, branches to, passes to a call or a tail call or returns, in its register, a copy or a vector register's lane, on some path that reads no memory through it, along both ways of a conditional jump and past calls in a callee-saved register, where the code at the address decodes and calls nothing outside the executable segments (position-independent code needs no relocation for them, and code that keeps strings and tables among its instructions reads memory through theirs instead, or returns them, as OpenSSL's `RC4_options` returns its option strings); a module's exports are how AnyPS5 reaches it. Once those reach nothing new, every 16-byte-aligned address that follows `int3` padding in code no discovered function covers starts a function too, unless the code from there does not decode or calls outside the executable segments (data can follow padding as well, as the version strings FreeBSD's assembly sources put among their code do, and an immediate operand can end in `int3`'s byte just before an aligned address), and discovery goes on from there: an interpreter's precompiled builtins, such as those of the V8 that Coherent's UI library embeds, are called only through offsets it adds at run time, so nothing else names them. Discovery decodes a function's instructions while it works on that function and then keeps only where each lies, its address and length, since a decoded instruction takes about 1.1 KiB and a large title has 39 million of them; the lifter decodes a function again from the image's bytes when it emits it. The functions of each image go into parts of their own, and one more part holds `ps5lift_program`: a table per image (the name `ld.so` would report, its load bias and mapped program headers, segments, TLS, imports, data imports, `DT_INIT` and `DT_INIT_ARRAY`), the order to initialize the modules in, which is a depth-first walk of their dependencies, and one sorted function table over every image for dispatch. Before the executable's entry point the runtime calls each module's `DT_INIT` and `DT_INIT_ARRAY` entries with `argc`, `argv` and `envp` on the main thread.

The images are not host shared objects, so glibc's `dl_iterate_phdr` cannot report them, yet AnyPS5 finds the executable's process parameters, its guest memory, module information and unwind tables through it. A lifted AnyPS5 build therefore calls the runtime's `GuestCpuIterateImages` instead, which reports each guest image as `ld.so` would: an empty name for the executable and the module's path from the executable's directory, the load bias, the program headers where the image maps them, and the TLS module ID and the calling thread's block.

Every image with a `PT_TLS` segment gets a static TLS block below the thread pointer, in load order, with the executable's nearest, as x86-64 lays out the blocks of the images loaded at start: the executable's local-exec offsets assume exactly that. Its module ID is its index plus one. `R_X86_64_DTPMOD64` becomes that ID, `DTPOFF64` the symbol's offset in its block and `TPOFF64` its offset from the thread pointer, all at lift time; each thread copies every image's initialization image into its block. `__tls_get_addr`, which a module imports from `ld-linux`, is defined by the runtime, since it takes `ld.so`'s place. `tests/fixtures/modules.c` runs an executable whose module's constructor calls an import, and which calls a module function directly and through a pointer, reads and writes the module's data, and uses its own TLS and the module's, and iterates the images through `dl_iterate_phdr`.

## Machine model

`Ps5LiftState` ([State.h](../../ps5lift/runtime/include/ps5lift/State.h)) holds the sixteen GPRs, the flags as bytes, the FS and GS bases, MXCSR and sixteen 256-bit vector registers. Each lifted function caches the registers its instructions name (explicitly or implicitly) in allocas: it loads them on entry, stores them back before every call, return, dispatch and runtime helper, and reloads them after. Registers a function never names stay in the state, where its callees find them. Discovery gives each function its register effects, closed over the functions it reaches through direct calls and jumps: the registers it names, whose values it carries through the state even where it does not change them, and those it may write. A direct call stores only the registers the callee names and reloads only those it may write. A function that reaches dispatch, an import, an interrupt, `fxsave` or `fxrstor` names and writes them all, so the runtime and the unwinder always find current values in the state. LLVM promotes the allocas to SSA values, so registers live in host registers within a function and flags nobody reads are deleted.

The status flags do not cross calls or returns, as the SysV ABI says; only DF does. Compiled code never reads flags its caller or callee left behind, and dropping them removes the flag and parity computations that would otherwise precede every call. `--preserve-flags` keeps them for hand-written assembly that does rely on them.

Guest memory is identity mapped: the runtime maps the image at its link addresses, so a guest pointer is a host pointer and a memory operand becomes one load or store. PS5 titles are the only goal, and their executables are position-independent (`ET_SCE_DYNEXEC`), so the relinker places each at 1008 GiB (`--linux-fixed-base 0xFC00000000`), and the fixtures are position-independent code linked there too. That is where the PS5 application area ends: a title allocates and reserves its memory below it, from 64 GiB, so the image never lies in a range the title asks for (an Unreal title reserves 512 GiB there). It is also above everything an arm64 macOS process keeps below 448 GiB, so every host has the same guest layout; code that needs to sit below 4 GiB, such as code with 32-bit absolute addresses, is not PS5 code. Native libraries can read guest structures directly; x86-64 SysV and AArch64 LP64 lay out ordinary C types the same way (`long double` and `va_list` differ).

The guest stack is real guest memory. `call` pushes the return address, the callee's `ret` pops it, and the host call returns; guest code that reads its return address or walks its stack sees what it would see on the console.

## Control flow

- Direct calls are host calls to `guest_<target>`.
- Direct jumps inside a function are branches; jumps or fall-through to another function's start are tail calls while RSP is back at the jumping function's entry, and so is an indirect jump that no jump table resolves, through the runtime's `ps5lift_resolve_jump`. They are `musttail` calls, which every guest function's one prototype allows, so a chain of tail jumps keeps one host frame even in an unoptimized lift. With RSP elsewhere the target can still return from the jumping function's frame, as code split off from a function does, or from another frame, as when V8 enters a handler on a stack it switched to or after pushing a return address for it, so the jump calls the target instead. Every lifted `ret` records in `ReturnSlot` the stack slot it took its return address from: the jumping function returns when that is its own slot and otherwise unwinds to the address in the slot. An indirect jump to an address that has no lifted function returns there, as V8 returns by popping its return address and jumping to it.
- Indirect calls go through `ps5lift_dispatch`, which looks up the target in a hash table the runtime builds from the sorted function table at start-up. A miss stops with the address, which names a function discovery has to find.
- Jump tables (position-independent `lea; movsxd; add; jmp`, which adds the table to the entry as clang does or the entry to the table as GCC does; PS5 code, being position-independent, has no tables at 32-bit absolute addresses) are recovered and lifted as an LLVM `switch` that falls back to dispatch, or stops the program when the table is closed: bounded by a guard, in a segment without `PF_W` and written by no relocation, so no other target can occur. Discovery reads the shape through the function's control-flow graph rather than its address order: the jump's register must be set by a single `add` (or `mov`) on every path, its addend by a single `movsxd`, whatever the scheduler put between them, and the base by `lea table(%rip)` on every path, set again or kept in another register by a 64-bit `mov` on paths that reused it, which lets the entry be loaded through one register and added to a copy of it; a call ends a path for a register the ABI does not preserve. Indirect jumps wait until the code reached without them is known, since a table's base is often set before a dispatch loop whose other entries only its cases reach, and each round of cases can resolve another table; once nothing more resolves, every table is read again with the whole graph, and one that reads differently stops the lift. The bound comes from the guarding `cmp` or `sub` with `ja`/`jae`, which compare unsigned at the guarded register's width, on the index, on a register it is a 32- or 64-bit `mov` copy of, or on the byte or word register it was zero-extended from (`cmp $22, %dl` before `movzbl %dl, %edx`, which a guard narrower than that register does not bound), found through instructions that each have a single predecessor, so the guard dominates the jump. A table without a recognised guard ends at the next address that code refers to as data, which a linear sweep of the executable segments collects before discovery, or at its first entry outside the function. `ps5lift` reports how many tables it sized that way.
- Every undefined symbol a relocation names gets a synthetic address past the image, and its slots are filled with it. Each such address is a lifted function that calls `ps5lift_import_<name>(Ps5LiftState*)` and pops the return address; `_` in the name becomes `__`, `+` `_p`, `-` `_m` and `#` `_h`. A `call` or `jmp` through a slot that holds an import is a direct call to it, and anything else that loads the slot reaches it through dispatch, so PLT stubs and PS5's `call [rip+slot]` both work. For PS5 titles the name is the NID, and the bridge calls the AnyPS5 implementation with arguments taken from rdi, rsi, rdx, rcx, r8, r9, xmm0-7 and the stack.
- Guest code can also leave a frame without `ret`. To unwind, the runtime puts the target's registers into the state, records the guest address to resume at and the stack pointer it resumes with, and sets `Unwinding`. Lifted code checks that flag after every guest call: a function with no resume point returns at once, without writing its cached registers back, and a function with resume points takes over when its entry stack pointer is at or above the recorded one, which only the target frame and frames outside it satisfy and the target is reached first. It clears the flag, reloads its registers and branches to the resume point. `longjmp` is the first user: discovery makes the return address of every call to a `setjmp`-family import (by name or NID) a resume point, and the runtime's `setjmp` and `longjmp`, which take every call to the family even when a guest module exports it (a PS5 title's own `libc.prx`, whose exports the relinker names `<NID>#guest`), since a module's `longjmp` may leave by a jump to the saved address, which lifted code cannot follow, ([Jump.cpp](../../ps5lift/runtime/src/Jump.cpp)) use AnyPS5's 96-byte `jmp_buf`, including its signal mask when AnyPS5's libc is linked in. The check costs a load and a branch that is not taken after each call; frames do not need unwind tables or landing pads.
- Guest C++ exceptions use the same mechanism. Every landing pad in a function's LSDA is a resume point, found through the image's `.eh_frame_hdr`. The guest's `__cxa_throw` reaches AnyPS5's exception runtime through its bridge, and AnyPS5's DWARF unwinder, built for a lifted guest, starts from the guest frame that called the import, finds frames in the guest's unwind tables through `dl_iterate_phdr`, resolves the personality routine from its import name and calls AnyPS5's own, and installs the landing pad's registers into the state. It then throws a host `GuestUnwind` exception, which every generated bridge catches. That leaves the native frames between the bridge and the unwinder, and the bridge returns into the lifted frames with the flag set.
- A title that ships its own `libc.prx` throws through its own unwinder, LLVM's libunwind, which runs as lifted guest code: it finds the unwind tables through `sceKernelGetModuleInfoForUnwind`, calls the title's personality routine, and installs the landing pad's registers with `jumpto`, which loads the landing pad's stack pointer from memory, pops `rdi` there and makes a `ret`. A function that gives RSP a value it does not compute from RSP (a `mov`, a `pop`, a `lea` from another base or a `leave`, but not `add`, `sub` or `and`) checks at each `ret` whether RSP is still the one it entered with. If not, the `ret` resumes at the address it pops: it records that address, the slot it took it from and the stack pointer after the pop, sets `Unwinding` and unwinds as after a guest call, so the frame that owns the landing pad takes over. A call takes over an unwind to its own return address when the `ret` took the address from the call's slot, as when V8 resumes a frame after a throw, or, for the first call the unwind reaches, from a slot above it, as a callee that pops its caller's stack arguments does; calls further out that wait at the same address, such as the recursive calls a thrown exception discards, let it pass. An unwind that no frame takes stops, and names the jump when a jump to code that was not lifted started it. A function that only adjusts RSP pays nothing; the others pay a compare and a branch that is not taken at each `ret`.
- An undefined data symbol (an `STT_OBJECT` import such as `_Stdout` or a `__cxxabiv1` type_info vtable) gets no synthetic address. The lifter records each slot that refers to it, and the runtime fills the slot with the address of `ps5lift_data_<NID>`, which the bridge generator defines for each variable AnyPS5 exports. `--import-nids` makes the lifter use the NID of a plain symbol name, so a guest built for Linux against libstdc++ reaches AnyPS5's exports.
- Relocation targets inside executable segments seed discovery, which is how function pointers in stripped images are found.
- The runtime enters the image the way Linux does, with `argc`, `argv`, `envp` and `auxv` at `rsp`, so the relinker's entry stub runs unchanged. It copies `PT_TLS` below the thread pointer (x86-64 variant II) and stores the thread pointer at `fs:0`.

## x87

The eight x87 registers, the tag bits, the control word and the status word (with TOP in bits 11-13) live in `Ps5LiftState`. Each x87 instruction becomes a call to `ps5lift_x87` ([X87.cpp](../../ps5lift/runtime/src/X87.cpp)) with an operation, an operand format and an address or register index; it needs no register flush, because it only touches the x87 state and guest memory. The arithmetic is Berkeley SoftFloat's 80-bit extended format with its 8086 specialization, which follows x86's NaN rules, built with thread-local state so each guest thread has its own rounding mode. On top of SoftFloat the runtime reproduces what the x87 adds: rounding and precision control from the control word (precision applies only to `fadd`, `fsub`, `fmul`, `fdiv` and `fsqrt`), the denormal-operand flag, C1 as the round-up indicator, stack overflow and underflow with the indefinite NaN, integer stores that write the integer indefinite value, C0/C2/C3 left unchanged by instructions that do not define them, and the exact low quotient bits of `fprem` and `fprem1`. `tests/fixtures/x87.c` checks arithmetic, comparisons, conversions, `fsqrt`, `frndint`, `fscale`, `fprem`, `fprem1`, `fxam`, the constants and the exception flags under every rounding mode and three precisions against native results.

MMX registers are the low 64 bits of the physical x87 registers in the state, as on the hardware. The lifter reads and writes them there directly; an instruction with an MMX operand sets TOP to 0 and marks every register valid, a write sets bits 64-79 of its register to ones, and `emms` marks them all empty. MMX arithmetic goes through the same vector code as SSE, with a 64-bit operand as one lane. `tests/fixtures/mmx.c` checks every MMX instruction EVO Player uses and that an x87 store sees an MMX value; Rosetta, which supplied the other expected values, does not alias the two and stores the indefinite value there.

### Guest long double

The guest's `long double` is the x87 80-bit format in a 16-byte slot. aarch64's binary128 holds every such value, but rounds each step to its own 113 bits rather than as x87 does. A lifted AnyPS5 libc keeps it in a class, `LibcDetail::GuestLongDouble` in [GuestLongDouble.hpp](../../core/libs/prx/libc/include/GuestLongDouble.hpp), laid out as the guest stores it. Its arithmetic, square root, rounding to an integer and conversions to `double`, `float` and integers call the runtime's x87 (`GuestCpuExtended*`), so they round, honour precision control and raise exceptions as the guest's control and status words say. Conversions from integers and doubles, comparisons, `frexp`, `scalbn`, `fmod`, `remainder`, `remquo`, `modf`, `logb` and the fixed-direction roundings work on the bits. `strtold` and `scanf("%Lf")` parse into it with exact big-integer arithmetic, correctly rounded in the guest's rounding mode, and `printf` formats its exact digits. A tool that compiles this code for an x86-64 host with x87 behind the runtime's entry points matched glibc's x87 `strtold` in 58,244 cases across the four rounding modes and the bit operations in 5.6 million. The transcendental functions are the exception ([known gaps](TechnicalDebt.md#ps5lift)).

A bridge passes the class as the runtime's `Bridge::LongDouble`, which has the same layout and is passed the same way: `Extended(state, slot)` reads an argument from its 16-byte stack slot and `ReturnExtended` loads a result onto the guest's x87 stack. A bridge for a function that takes the host's `long double`, which only an x86-64 or binary128 host can declare, converts with `HostExtended` instead.

## Variadic imports

A guest `printf` passes its arguments the SysV way, and an aarch64 host cannot express that call with its own `va_list`. Every variadic AnyPS5 export has a `v` sibling that takes a `VaList*`, a pointer to the SysV `va_list` structure, so the bridge for a variadic export builds that structure and calls the sibling: `VariadicArguments` in [Bridge.hpp](../../ps5lift/runtime/include/ps5lift/Bridge.hpp) copies rdi to r9 and xmm0 to xmm7 into a register save area, sets `gp_offset` and `fp_offset` past the named arguments and points the overflow area at the guest stack. Guest code that builds its own `va_list` and calls `vsnprintf` passes it through unchanged.

In a lifted build AnyPS5's libc reads every `VaList` with its portable formatter (`FormatArguments`, the code its Windows build uses) instead of handing it to the host's `vprintf`, and scans with its in-process scanner. Host code that calls the libc's own `...` functions, such as the libc itself or upstream's tests, wraps its `va_list` in a `VaList` tagged with `gp_offset = 0xffffffff` (`APS5_VA_BEGIN` in [GuestVaList.hpp](../../core/libs/prx/libc/include/GuestVaList.hpp)), and `FormatArguments` reads that one with `va_arg`. The lifted libc keeps the host's C++ runtime and personality routine instead of replacing them with AnyPS5's guest unwinder, so its own `throw` and `catch` work on aarch64. When the libc is linked in, its guest arena has reserved the PS5 user address range, and the runtime commits the guest image inside it.

The generator follows the rule AnyPS5's NID patcher applies to a built library: every `extern "C"` function or variable a library defines is an export, named by the NID of its name without `_nid_postfix` or `_nid_disambigN`, unless it ends in `_nid_no_patch`; `_nid_no_patch_cut` and `APS5_EXPORT` give an explicit NID. Bridges for several libraries go into one file, and a NID that more than one exports (libkernel re-exports most of libc) is bridged to the first library named. The program links the libraries as the shared objects AnyPS5's build makes before NID patching, libc first, so the dynamic linker binds the few functions two of them define (`exit`, `rename`) to libc's. A variadic export without a `v` sibling, such as `open` or `fcntl`, receives the guest's remaining integer argument registers as extra arguments, which is where an aarch64 or x86-64 host's `va_arg` reads them.

libkernel built for a lifted guest reads the timestamp counter through the runtime (`cntvct_el0` on aarch64), as the lifted `rdtsc` instruction does. A guest thread's entry point arrives in `scePthreadCreate` as a callback thunk, so the new host thread runs it on a guest state of its own. libkernel maps that thread a guest stack of the size the guest asked for, above a guard page, reports it as the thread's stack and hands its top to the runtime (`GuestCpuUseStack`) before the entry runs; the host thread's own stack holds only lifted frames and is the size the runtime gives (`GuestCpuHostStackSize`). A handler that `sceKernelRaiseException` delivers runs on the interrupted thread, on an interrupt stack the runtime maps for each thread, since lifted code keeps the guest's stack pointer in a host register between calls and the one in the state can lie above live frames. It sees the guest registers as of that thread's last call, with `rip` that call's return address, which every lifted call stores, and leaves them and the MXCSR unchanged.

libSceFiber built for a lifted guest gives every fiber a host stack of its own (the context size plus 16 MiB, reserved but not committed) and switches host stacks with its own assembly, an aarch64 version beside the x86 one. Around each switch it saves the guest's callee-saved registers, stack pointer, MXCSR and x87 control word through `GuestCpuSaveFiber` and restores them through `GuestCpuRestoreFiber` once the fiber that switched away runs again. A fiber starts with its guest stack pointer at the top of its guest context and calls its entry, a callback thunk, on the running thread's guest state. The lifted frames on its stack keep that state, so a suspended fiber resumes only on the thread that started it; resuming it on another thread stops with an error ([known gaps](TechnicalDebt.md#ps5lift)). `tests/fixtures/fiber.c` switches two fibers back and forth, returns to the thread, then resumes a third fiber on another thread and expects that stop.

`tests/fixtures/libc.c` is a guest that calls `printf`, `snprintf`, `vsnprintf` with its own `va_list`, `sscanf`, `strtold`, `strtod`, `modfl`, `fabsl` and `puts` by NID. It is lifted and linked with the generated bridges, the libc built in lifted mode and the runtime, and its output is compared with `libc.expected`, which matches glibc except where AnyPS5 prints `long double` digits the way the console does. `tools/ps5lift.py libc-tests` builds upstream's libc tests against the same libc.

The bridge generator tells libclang's cursors apart by their raw kind, since a header can hold a cursor newer than the bindings, such as a C++20 requires-expression in libstdc++ 14. In the test build each library fixture's bridges are generated once, from the libraries it calls, and AnyPS5's lifted libraries link the runtime built for the host and are built for the CPU the runtime is built for, since they share the process. The fixtures build without unwind tables, so `kernel.c` brings an `.eh_frame` of its own, and it checks that a thread handle lies in the process's own memory, below the end of the application area, as on the console. A lifted build's `dlopen` takes the lifted image whose path from the executable's directory ends the path it resolves, with or without the relinker's `.guest.prx`, and opens any other path as a native library; `loader.c` loads a title module through its `/app0` path and a native library of the same name through its system path, and checks that each load finds its own and that `dlopen(NULL)` returns the executable's module ID.

## Callbacks

Native code cannot run guest code as its own. A bridge that receives a function pointer passes the native code a thunk instead: `Callback<R(Args...)>(guestAddress)` in [Bridge.hpp](../../ps5lift/runtime/include/ps5lift/Bridge.hpp) returns one of 256 compile-time thunks per signature, the same one every time for the same guest address, so pointer comparisons keep working. Values that cannot be code pass through unchanged, since callees read them as conventions: anything in the null page, where `NULL`, `SIG_DFL`, `SIG_IGN` and `SIG_HOLD` lie, and all ones, which is `SIG_ERR`. A thunk places its arguments in the SysV registers and on the guest stack, pushes a return address and calls the lifted target through dispatch on the calling thread's guest state.

A pointer native code reads from guest memory, such as a callback a guest stored in a structure, never passes through a bridge, so native code calls the guest address itself ([NativeCall.cpp](../../ps5lift/runtime/src/NativeCall.cpp)). Guest code is mapped without execute permission, so the call faults on its first instruction, with `SIGBUS` on aarch64 when the function's address is not a multiple of four; the runtime's `SIGSEGV` and `SIGBUS` handler, which passes every other fault to the handler before it, sends a fault at the start of a lifted function to a trampoline with the guest address in a scratch register no call preserves. The trampoline saves the host's first eight integer and eight vector argument registers, which become the guest's six integer registers, two stack slots and eight vector registers, calls the lifted function as a thunk does, and returns `rax`, `rdx`, `xmm0` and `xmm1` in the host's result registers. That serves every signature whose arguments and result are scalars in registers; arguments the host passes on its stack and records returned through memory do not cross, and each call costs a signal. A fault elsewhere in a guest image stops the program, naming the address.

The runtime keeps each guest thread's state in a thread-local. A native thread that calls a thunk without one, such as a thread a native library started, gets a guest stack of 8 MiB above a guard page, a TLS block and a state on its first call, which is how a native `pthread_create` or a worker pool can run guest code. Such a thread's own code keeps the host's floating-point environment: its outermost callback switches the host FPU to the guest's MXCSR and back when it returns, keeping the exception flags the guest raised for its next callback, and native code that only queries the guest state changes nothing. A thread-specific key releases the state when the thread exits, after its `thread_local` destructors, so a callback from one of those still has a stack. Native code that a bridge calls runs in the guest's environment, as the console's libraries would, and a thread it starts inherits that environment.

## Target instructions

AES-NI and `pclmulqdq` have no target-independent LLVM form, so the lifter, which knows the target triple, emits the target's own instructions and code generation enables them (`aes` on aarch64, which LLVM ties to `PMULL`; `aes` and `pclmul` on x86-64). On aarch64 `aesenc` is `AESMC(AESE(state, 0)) ^ key`: `AESE` adds its key before it shifts rows and substitutes bytes, while x86 adds the round key after mixing columns, so it takes a zero key and the round key follows. `aesdec` is `AESIMC(AESD(state, 0)) ^ key`, the `last` forms drop the column mix, `aeskeygenassist` shifts its source's rows back before `AESE` so that only the S-box applies, and `pclmulqdq` is `PMULL` on the selected halves. The runtime stops at start on a host without AES and PMULL, since its `cpuid` reports them. SSE4.2's string comparisons (`pcmpestri`, `pcmpestrm`, `pcmpistri`, `pcmpistrm` and their VEX forms) call a runtime function that follows the SDM's description of the control byte, element by element, and the lifter derives the index or mask and the flags from its result; `tests/fixtures/strings.c` runs every control byte over random strings and compares hashes taken on an Intel CPU. The SHA extensions do not map onto the crypto extension's SHA1 and SHA256 instructions, which keep the state in other halves and round in fours, so they are lifted as the SDM defines them: rotates, choose, majority and parity on 32-bit lanes.

## Memory ordering

x86 is TSO; the GB10 cores have no TSO mode. With `--memory tso` every guest load is an acquire load and every store a release store, except the stack accesses of `push`, `pop`, `call` and `ret`, the accesses to a private frame, and the exceptions in [known gaps](TechnicalDebt.md#ps5lift). A frame is private when no instruction of its function hands out an address in it, by copying `rsp`, the frame pointer or an address computed from them into memory or another register, as `lea 0x10(%rsp),%rdi` does; no other thread can reach it then. Its accesses through `rsp` are plain, and through `rbp` when the function starts with `push %rbp; mov %rsp,%rbp` and nothing else writes `rbp` but the `pop %rbp` or `leave` that restores it. A function whose frame escapes orders them all. A load through `rip` with no index that lies wholly in a segment without `PF_W` is plain too, since nothing writes there: the runtime stops a guest that makes such a segment writable (`GuestCpuMakingWritable`). The saved registers and return addresses that `push`, `pop`, `call` and `ret` touch are out of reach of any pointer a function hands out. On a CPU with FEAT_LRCPC (`neoverse-v2`, the GB10) acquire loads become `LDAPR`, which is cheaper than `LDAR`. Both fault on an address that is not naturally aligned, which the GB10 relaxes only within 16 bytes, while x86 code may use any address, so each ordered access wider than a byte tests its alignment: an unaligned one is a plain access followed by `DMB ISHLD` for a load and preceded by `DMB ISH` for a store, which orders it as TSO requires. Locked instructions, `xchg` with memory, `xadd` and `cmpxchg` are sequentially consistent LLVM atomics, lowered to LSE. `mfence` is a full fence. `clflush` and `clflushopt` become `DC CIVAC` and `clwb` becomes `DC CVAC`, through the runtime, so a line the guest writes back for an observer that does not snoop its cache still reaches memory.

qemu 8.2 computes the address of `STLUR` and `LDAPUR` with a negative offset wrongly; the test driver turns off `rcpc-immo` when it runs aarch64 code under qemu, and runs it with `-one-insn-per-tb` (see [known gaps](TechnicalDebt.md#ps5lift)). Real hardware is not affected by the first.

Guest memory accesses and register-state accesses carry distinct TBAA tags. The state is host memory that guest code cannot address, so LLVM may keep registers in host registers across guest loads and stores and drop redundant state traffic.

## Arithmetic

Flags are computed exactly for add, adc, sub, sbb, cmp, logic, inc, dec, neg, shifts and rotates (including the count-zero case), the multiplies and the BMI1/BMI2 instructions. Shifts are computed in 128 bits so no LLVM shift is ever poison. AF is computed for arithmetic and cleared for logic.

## Floating point

`--float exact` (the default) reproduces SSE and AVX results bit for bit, including NaNs, which LLVM otherwise leaves unspecified:

- A NaN result is the first NaN source, quieted: the first operand for two-operand arithmetic, and for FMA the left multiplicand, the right multiplicand, then the addend, as measured on an Intel host. Invalid operations without a NaN source give the negative default NaN (`0xffc00000`, `0xfff8000000000000`).
- `min` and `max` return the second operand when either is NaN or both are zero, and under DAZ return a denormal operand as a signed zero.
- Conversions to integers return the integer indefinite value (`0x80000000`, `0x8000000000000000`) for NaN and out-of-range inputs; float, double and half conversions carry NaN payloads as x86 does; `vcvtps2ph` with an immediate rounding mode is computed in integer arithmetic so it ignores the dynamic mode.
- Scalar instructions merge into the destination (legacy) or the first source (VEX) and zero bits 128-255 for VEX.
- `ldmxcsr` stores the guest MXCSR and calls the runtime, which sets the host rounding mode and flushing: on aarch64 either DAZ or FTZ sets `FPCR.FZ`, which flushes inputs and outputs alike and judges a result tiny before rounding, where x86 does after. `FPCR.AH` would flush them apart as x86 does, but it also makes `FNEG` and `FABS` leave a NaN as it is, and LLVM builds constants with `FNEG` (LLVM 23 and Xcode's clang do, LLVM 18 does not): the double sign mask `0x7fffffffffffffff` as the negation of all-ones, which under `AH` stays all-ones. Code from either compiler, the lifted program and the host's libraries alike, would compute with the wrong masks, so the runtime leaves `AH` clear. Guests start with the console's MXCSR, `0x9fc0`.
- The NaN rules above are computed, not left to the host: `NanResult` passes the host's result through `llvm.arithmetic.fence` before it picks the NaN, because LLVM lets an operation that produces a NaN produce any NaN and so may drop a select that only picks another one. LLVM 23 does after a square root.

`--float fast` drops the NaN and DAZ handling and leaves NaN payloads to the host.

## Implementation notes

### Build

- `ps5lift` links LLVM's shared library, as LLVM's own tools do: Ubuntu's and Homebrew's packages keep it consistent with the libraries it depends on, such as z3, when those are upgraded, where the static libraries name the versions installed when `ps5lift` was built. [LlvmCompatibility.hpp](../../ps5lift/lifter/src/LlvmCompatibility.hpp) covers the API differences between LLVM 18 and 23: a target triple as text or as `llvm::Triple`, a subtarget as a pointer or a reference, `getTerminator()` against `hasTerminator()`, and a feature's name in `Key` or behind `key()`.
- Code generation turns off AArch64's complex deinterleaving pass, which in LLVM 18 and 19 can place the `llvm.vector.deinterleave2` it forms after a use of its result, where the instruction scheduler crashes on it; lifted x86 code has little complex arithmetic for it to form. x86-64 output enables LLVM's `crc32` feature, which its `sse4.2` does not imply.
- The runtime must not need a CPU feature that the lifted code it serves does not, so `tools/ps5lift.py runtime --cpu` builds it for that code's CPU, as the lifter's `--cpu` names it. Left out, that is the lifter's default, `neoverse-v2` on aarch64, which also gives the runtime LSE atomics instead of calls to the outline atomic helpers. The test drivers build it for the CPU they lift for: the host's (`native`) when the lifted code runs natively, where clang 18's `-mcpu=native` does not know the GB10's cores and falls back to a generic CPU that calls those helpers, and the lifter's default under qemu. Each CPU's runtime has a directory of its own. Tests that run in parallel share it, so it builds under a lock and replaces each output whole, and it links an output again whenever one of its objects is newer, as a link that failed or was interrupted after the compile leaves it.

### Discovery

- A jump table's index after a zero extension is the narrow register it came from, so its guard has to compare at least that much. Zydis sign-extends a guard's immediate to 64 bits, so `cmpb $0xab, %dl`, which bounds 172 entries, reads as a bound past any table until the immediate is cut to the register's width. Clang adds the table to the loaded entry and GCC the entry to the table; the entry can be loaded through one register and added to a copy of it, and the scheduler can move other instructions between the load, the addition and the jump.
- A table is closed when a guard bounds it and it lies in a read-only segment that no relocation touches: then its targets are all its jump can take. Its targets lie in the code between the function starts around the jump, which is the function's own code unless the function jumped into code another one starts, as functions that share a tail do. A table's base or guard can lie on a path that only another table leads to, so tables are recovered once the code reached without them is known, and again after each round of code they reveal.
- An instruction that another one overlaps, such as a `cmpxchg` after a `lock` prefix that a jump skips, continues at its own end, which then starts a block of its own.
- Each round decodes the new starts and again only the functions they can change, those whose instructions or table targets span one, so a chain of functions that each name only the next, as a state machine's states do, costs a round per link but not a pass over the image.
- A function's effects are the registers it names, which it loads from the state at entry and stores back at its return, and those it may change, each with those of every function it reaches through direct calls and jumps, iterated until nothing changes, as recursion needs. A function that reaches dispatch, an import, an interrupt, `fxsave` or `fxrstor` names and changes them all, and an exit that starts no function counts as unknown code. A call stores the registers its callee names and reloads those it may write; the rest keep their cached values.
- A call to `setjmp`, `longjmp` or one of their variants goes to the runtime even when a guest module exports it, as the relinker names a module's export `<NID>#guest`, since only the runtime can save and restore the guest's registers for lifted code.

### Lifting

- An instruction that gives `rsp` a value it does not compute from `rsp`, as a context switch does when it loads the stack pointer it switches to, leaves the stack the function runs on. `leave` is one: it takes `rsp` from `rbp`, which code split off from a function and entered by a jump did not set. A `ret` on another stack, as libunwind's `jumpto` makes after it loads the landing pad's `rsp`, continues at the address it pops in the frame that stack belongs to, and the host frames below unwind to that frame as they do for a `longjmp`.
- A function's frame is private when no instruction of the function hands out an address in it: copying `rsp`, or `rbp` when the function keeps it as its frame pointer (it starts with `push %rbp; mov %rsp,%rbp` and nothing else writes `rbp`), or an address computed from them, into memory or another register; `enter` hands one out.
- aarch64's acquire loads and release stores fault on unaligned addresses, which x86 allows, so an ordered access checks its alignment, and an unaligned one is a plain access with a fence after it if it is a load and before it if it is a store. The runtime reads and writes an x87 memory operand with `memcpy`, so under TSO the call is fenced on both sides. A string instruction is ordered with the code around it but not its elements with each other, as x86's fast strings are; the runtime runs `movs` as `memmove` unless the destination starts inside the source, where each element repeats one written before it, and `stos` of bytes as `memset`.
- x86 raises a divide error for a zero divisor or a quotient wider than the operand, which LLVM leaves undefined, so those stop before any division. A dividend whose high half only extends its low half, the usual case, divides at the operand's width, since aarch64 has no instruction for twice it.
- A register bit offset of `bt` and its kin is signed and indexes a bit string that starts at the memory operand, so it can select an operand-sized unit before or after the one named; an immediate offset stays in the operand.
- Zydis sizes the register operands of legacy scalar instructions as their scalar, and the register source of `vbroadcastss` and `vbroadcastsd` as the whole register; the lifter works on the whole register, whose upper lanes are the result's, and takes the broadcast element from the mnemonic.
- `crc32` is the Castagnoli CRC that aarch64's CRC32C instructions compute, without the final inversion. AESE and AESD add the round key before they substitute bytes, where x86 adds it after mixing columns, so they take a zero key and the round key follows, and AESE shifts rows first, so the source is shifted back. The SHA extensions are lifted as the SDM's 32-bit lane arithmetic, since aarch64's SHA1 and SHA256 instructions split the state differently and round in fours.
- SSE4a's `extrq` and `insertq` keep the destination's upper quadword, which AMD leaves undefined; a field past bit 63, also undefined, and the forms that take the field from a register are unsupported. `vmaskmov` and `vpmaskmov` access only the elements whose mask element has its sign bit set, so a masked-off element cannot fault.
- `fxsave` and `fxrstor` move every vector register without naming them, so the cached registers are written back before either and read again after `fxrstor`. `loop`, `loope` and `loopne` count down `rcx`, or `ecx` under an address-size prefix, without changing the flags.

### Runtime

- The runtime is a shared library that cannot name the lifted program, so the program's `main` hands it `ps5lift_program` before anything asks for it. Dispatch looks a guest address up in an open-addressing table with linear probing, a power of two in size and at most half full, built when the program is handed over and only read after; an empty slot holds guest address 0, where no function starts.
- A thread that runs guest code has a state, a guest stack unless its creator gives one, a TLS block and a stack for exception handlers, since the stack pointer of the code they interrupt is only known as of its last call. A native thread keeps the host's floating-point environment and switches to the guest's only while a callback runs; one that jumps out of its callbacks, as `scePthreadExit` does, keeps the guest's until it exits. The key that holds a thread's state has a destructor that runs after the thread's `thread_local` destructors, so a callback from one of those still finds its state.
- A native call into guest code faults with `SIGSEGV`, or with `SIGBUS` on aarch64 when the address is not a multiple of four, which no branch there can reach, and the handler treats both alike.
- `clflush` and `clflushopt` become `DC CIVAC` and `clwb` `DC CVAC`; an x86-64 host flushes for both, since `clwb` is optional there. `cpuid` reports the AES-NI, PCLMULQDQ and `crc32` of the PS5's Zen 2, which lifted code runs on the host's own instructions, and `xgetbv` with ECX=1 reports every enabled component as in use. A guest interrupt stops the program and reports the code the console's libc stores at `%fs:0x28` before it raises one.
- A host `long double` holds every x87 value only where it is x87's own format or IEEE binary128; on macOS for arm64 it is a `double`. The MXCSR mask holds every bit the guest may set, DAZ included, as `fxsave` reports it on the console's processor.
- Images are numbered from 1 in the order the lifter loaded them, the executable first, and each image's exports are sorted by name. The runtime finds an image by name ignoring the case of ASCII letters, as AnyPS5 resolves the console's file names, and reports it to `dl_iterate_phdr` callbacks in glibc's and FreeBSD's `dl_phdr_info` layout.

### Tests

- `basic.c` covers the discovery cases above: functions that only a RIP-relative `lea` names, stored, passed to a call or a tail call, returned, pushed, picked by a conditional move, kept in a callee-saved register across a call or paired with another pointer in a vector register; a function whose returned address is data that does not decode, as OpenSSL's `RC4_options` returns its strings; a function that only `int3` padding marks; tables indexed by a zero-extended byte or loaded through a copied base; a jump into another function's body; a jump into a locked `cmpxchg`; two functions that tail-jump to each other more times than an unoptimized lift's host frames would fit in the host stack; and bit strings.
- `vector.c` checks FIPS-197's AES-128 example and FIPS 180's SHA-1 and SHA-256 of "abc" with the dedicated instructions; the legacy encodings come from assembly and the VEX ones from intrinsics. `sse41.c` hashes a `dpps` or `dppd` result as one canonical NaN when two or more selected products are NaN or infinite, since x86 implementations add them in different orders. `x87.c`'s `fxsave` check hashes only what every processor writes alike, and loads MXCSR first, since a lifted guest starts with the console's and a native one with Linux's. `bench.c` calls 65,536 functions through a table, so each call goes through dispatch.
